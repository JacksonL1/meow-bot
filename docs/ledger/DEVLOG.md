## 2026-10-29 · 觉得它「圆」，先别缩放，看它是不是个正椭圆

用户的原话：「肚子现在太圆了。还有一处是像脏了一样，微调一下布偶猫的身体」。两句话是两件事，第二句比第一句好修。

**先说"像脏了"的那处**：它是 `#rig-torso-patch`，一个 `<ellipse cx="112" cy="134" rx="34" ry="18" fill="#EFE6DC" opacity="0.65"/>`，注释写的是**「背部柔毛轮廓」**。读起来却是污渍，四个原因叠在一起：在一只有 3.5px 描边的猫身上它是唯一**没有轮廓**的形状、它比身体**暗一档**、位置**偏右上**（不对称的东西会被当成意外而不是设计）、边缘是硬边没有羽化。删掉之后世界安静了——白猫的肚子本来就该是白的，体积感由描边 + 呼吸缩放 + 地面阴影三样提供，不需要再叠一块"暗部"。

- **一个注释说 A、看起来像 B 的部件，它实际上就是 B**。「背部柔毛轮廓」是当初写它的人给自己的行为找的解释；用户第一眼把它读成脏东西，那它就是脏东西。**注释描述意图，观感才是事实**——两者打架的时候信后者。

**再说"太圆"**：第一反应是调 `rx/ry` 缩一圈。但真正的圆感来源不是尺寸，是**曲线本身**——`#rig-torso` 是个 `<ellipse rx="54" ry="32">`，完美椭圆弧上每一点的曲率都在说"这是个圆"，而**动物身上一处纯椭圆轮廓都没有**。

- **判断"该改数值"还是"该换曲线类型"的办法**：把它在脑子里缩放一下，那个别扭的感觉会不会跟着缩放一起消失？椭圆缩到任何比例仍然是椭圆，所以"圆"这个感受会跟着缩放一起留下来——说明它在曲线类型里，不在数字里。这时候改数值只会让你在**"缩到露出缺口"和"放到还是个球"**之间来回弹，而且会一直以为是自己数值没调好。

- 试了四版才定：① 直接收窄到 92 → 头宽 104、肩只有 92，**头底两侧悬空 13px 的缺口**；② 加平底但肩太陡（`C118 106 132 120 140 140`）→ 像一顶**斗笠**；③ 底缘拉成 `Y=177.5` 直线 → 生硬；④ 定型为手绘 path：**肩 y112 宽 56（被头完全盖住）/ 腰 y146 最宽 100 / 底 y177 收成略平的圆角**。
- **改主形状要连它的邻居一起算**，一个"微调身体"的请求实际动了 4 个节点：后爪（原来 `cx52/152` 贴着身体侧面，收窄后会变成两块白圆片 → 移到 `cx57/143`，现在只在底部左右各露一牙月牙）、前爪（`cx68/132` 必须仍然在体内）、working 的键盘（`y162` 起，别让腰把它挡掉或架空）。

## 2026-10-29 · 台账上的数会过期，而且过期得不声不响

回写台账时顺手 `wc -l` 了一遍，发现 `PROJECT.md` 头部写的是「25 个源文件，约 7625 行（`src/` 4584）」，实数是 **21 个 / 7028 行（`src/` 3987）**。差了 597 行，全在 `src/` 里——大概率是某一轮"重写"之后留下的旧数（`renderer.js` 曾经更长），从没有人回头减掉。

- 这不是"忘了更新"，这类数字**本身就记不住**。它会一直对每个读台账的人说谎，直到有人 `wc -l`。
- 所以现在把**实测日期一起写进去**：「这个数是 2026-10-29 重新跑出来的」。写上日期之后，下一次读的人能立刻判断它过期了多久——一个没有日期的行数和一个有日期的行数，可信度不是一件事。
- 同一批还发现 `renderer.js` 记的是 1475 行、实数是 1476 行。**差 1 行也要改**：一行之差不会让任何人做错决定，但一个"行数是概数"的台账，跟"这几条断言大概是通过的"的台账属于同一种东西（硬约束 2）。

## 2026-10-28 · 「能有过渡吗」问的不是状态，是**哪里还是布尔**

用户的原话：「鼠标经过布偶猫的时候，如果处于睡觉状态，就慢慢让她变为 idle 状态，**能有过渡吗**」。
如果只按前半句做，改一行 `state = "idle"` 就"完成"了——而用户真正想要的恰好在最后那半句。

- **先分清哪件事根本不需要写代码**：躯干、头、耳、尾那 28 个弹簧通道本来就是二阶跟随，`setTarget()` 之后自然有过冲和滞后。`sleeping → idle` 的姿势差（bodyY 8.5 → 0、headY 13.5 → 0）不需要任何"过渡代码"，它自己会走。
- **再找哪里是布尔的**：眼睛。`eyeMode` 是个字符串（`open` / `sleep` / `happy`），代码按它**直接切 opacity 0/1**。整只猫里唯一会"啪"一下的就是这里，而它恰好是最显眼的地方——观察者先看脸。于是加一条 `eyeOpen` 弹簧（0=闭 1=睁，临界阻尼 ≈0.5s），三层眼睛交叉淡入。
- **顺带发现第二处硬切**：头顶的 zZz 是按 `state === "sleeping"` 切的。眼睛慢慢睁开、Z 却"啪"地消失，比不改更假。让它跟 `eyeOpen` 读同一个值——**同一个语义只能有一条曲线**，两处各算一遍迟早会错位。
- **反过来也要守住**：眨眼仍然硬切。150ms 的事，走弹簧会变成"慢慢眨眼"，看起来像卡住了。**"该慢的慢、该快的快"是两件事，别为了统一把两者都塞进弹簧。**

## 2026-10-28 · 一次"红了但功能是好的"失败，成本和真 bug 一样高

不透明度从 `"0"/"1"` 改成连续值（`0.000`~`1.000`）之后，回归里那条「会眨眼（睁眼层被藏起来过一次以上）」红了。
功能是好的，猫真的在眨——**红的是断言**：`if (v === "0")` 永远不成立。

- 这是硬约束 24（期望值别按字符串比）的**第二次复发**，上一次是 `style.transform` 的 `3.80px → 3.8px`。两次都是「我自己刚改的写入方式，把一条老断言的判据悄悄作废了」。
- **它不是无害的**：看到红项的第一反应是回去看渲染代码，而代码是对的。查这种失败花的时间不比查真 bug 少，而且它教人一个坏习惯——"这条红了大概是测试的问题"。**一旦养成这个习惯，真红就没人看了。**
- **所以加一条判别顺序**：先问「这个值的写入方式我最近改过吗」。改过就先看断言，没改过再看代码。

## 2026-10-28 · 删部件时，探针会从「真的是在变」悄悄变成「missing 也在变」

删掉胸口大毛领 `#rig-ruff`（只跟呼吸联动的装饰件）时，`src/` 里的 9 处引用都清干净了。
但回归里那条「每帧都在重算」的探针读的是 `['rig-body-group', 'rig-ruff', …]` 的 transform。

- **不改成 `missing:rig-ruff` 会怎样**：`elementFromPoint` 那类代码返回 `'missing:' + id`，这个字符串**每帧都一样**，所以"不同快照数"会从 4 项掉到 3 项——**这条断言很可能还是 PASS**（判据是 `>= 6/12`，另外三项还在变）。它不会红，只会变弱一档。
- **更糟的版本**：如果那个部件是唯一在变的（比如只有它含 `breathCos`），字符串就变成 `missing:rig-ruff` 这个**恒定值**，`Set` 大小 1，断言红——于是你会去"修探针"，而不是"想起自己删了个部件"。
- **教训**：删部件不是纯 SVG 改动。凡是有断言在读具体 id 的地方，都是这个部件的"第二处引用"。**外观改动也要 grep 一遍回归脚本**（`grep -rn "rig-ruff" scripts/`）。

## 2026-10-28 · 半改状态比"改错"更麻烦：先删会抛异常的那一行

批量清引用时脚本因为引号转义在第一条替换上就 `process.exit(1)` 了（**这是对的**——它先校验全部命中再写盘）。
但前一步的 Edit 已经把 SVG 里的 `#rig-ruff` 删掉了，于是仓库处于半改状态：**SVG 里没有它，`els.ruff` 还在 `querySelector` 它**。

- 那一刻的代码不会报错，只会在下一个 60fps 帧里对 `null.style` 抛 TypeError——**整只猫不画，控制台一屏红**。
- **顺序上的教训**：当一次改动跨"定义"和"消费"两侧、又不保证原子时，**先删会抛异常的那一侧（消费者），再删定义**。反过来的窗口期是"代码炸了但看不出原因"，正过来的窗口期只是"有个部件不显示"。
- **工具上的教训**：批量替换脚本的价值在于"全部命中才写盘"，所以它**必须**在失败时保持零改动（这次做到了）；但也意味着不能把"改定义"和"改引用"拆成两次工具调用混着来。

## 2026-10-28 · 先把死路走完，再回来盖房子

用户问「能不能直接和桌宠说，然后发送到 WorkBuddy」。我先花了半轮去证明三条路里前两条走不通：

| 路 | 不通的理由 |
|---|---|
| `codebuddy -p` | `--version` 是通的（2.165.0），但先是 `EADDRINUSE 127.0.0.1:51650`，加 `--port` 后暴露出真问题：`Authentication required`。桌面端登录态存在 Electron 的加密存储里，CLI 读不到。**而且就算登录了，`-p` 只开新会话** |
| 直接 POST `127.0.0.1:51650` | 端口属主确实是 `WorkBuddy.exe`。但那是未公开的内部接口——一次更新就崩，还等于绕开它自己的鉴权 |
| hook 的 stdout | 官方文档写死的契约 |

- **教训一**：这三条"不通的理由"必须写进台账。不写的话，下一个人（包括三个月后的我）会把它们重新走一遍，而且很可能在第一条上就得出"这个功能做不了"的结论。
- **教训二**：**造通道之前，先找已经存在的、有契约的通道**。这个项目里 hook 一直是"外面 → 桌宠"的单向管道，我默认它是单向的；实际上宿主早就在 `UserPromptSubmit` 的 stdout 上开了一个反向的口子，只是没人用过。
- **教训三**：用户说「可以试」的时候，试的价值在于**得出一个确定的结论**，不在于试成功。这次结论是"CLI 这条路对桌面端用户不成立"，这句话比代码更值钱。

## 2026-10-28 · 在被读到之前，stdout 不是日志，是协议

排版这段时一直有个别扭：文件头的铁律写着「绝不打日志，stdin 里有用户 prompt」。
而 `deliverLetters()` 恰恰往 stdout 写字。

- 想清楚了就不矛盾：**那几行字节不是给"人"看的诊断信息，是给宿主解析的协议输出**。铁律要防的是"把用户的 prompt 打进控制台/日志文件"，不是"不许和宿主通信"。
- 但紧跟着一个真问题：**没有信的时候必须一个字节都不输出**。`UserPromptSubmit` 的 stdout 会被并进用户这一轮的消息里，多打一个换行都是在污染**每一次**对话。所以这条做成了回归断言，用真子进程数 `out.length === 0`，不靠读内部变量猜。
- 还有一个更阴的坑：`process.exit(0)` 在管道上**会截断还没 flush 的输出**。截断的 JSON 在宿主那边就是"没有输出"——信白寄，而且零报错。所以输出改成了 `await new Promise(r => process.stdout.write(payload, r))`，写完再退。
- **教训**：凡是"写完就退出"的短命进程，都要问一句"我写的东西真的落地了吗"。这类 bug 的特点是**只在大 payload 或慢管道上出现**，本地手测永远碰不到。

## 2026-10-28 · "顺序"这种用户能感知的属性，别交给 UUID 兜底

回归里「取信按写入顺序、一封不漏」红了。一开始以为断言写错了，查下去是**真 bug**：

- 信按 `createdAt` 排序，`createdAt = Date.now()`。两封信完全可能落在**同一毫秒**里，这时排序走进兜底分支 `a.id < b.id`——而 id 是 UUID，**等于随机**。
- 于是"先写的先寄出"这个用户唯一能感知到的语义，在快写的情况下就没了。手写碰不到（人的手速不会同毫秒），脚本和回归能碰到。
- **修法**：`createdAt` 至少比现有最晚那封晚 1ms。代价是时间戳可能超前几毫秒，对 24h 的过期判断毫无影响。
- **更值得记的是断言**：我一开始只验"第一封排在最前面"。这条在 bug 存在时**也可能通过**（碰巧）。所以补了一条直接验不变量——`letters.every((l,i,a) => i===0 || l.createdAt > a[i-1].createdAt)`。**验结果不如验不变量：结果可能碰巧对，不变量不会。**

## 2026-10-28 · 别自己发明握手，用宿主的事件

信纸窗口第一次打开时有个经典问题：`loadFile` 是异步的，页面脚本还没跑完就 `send` 消息，消息会丢。

- 气泡窗口的解法是**握手**：渲染层注册完监听器后回发一个 `letter:ready`，主进程收到才投递。这在本项目里是有历史的（S5 踩过"第一个权限气泡永远空白"）。
- 但信纸这里我改用了 `did-finish-load`。差别在于**可靠性归属**：
  - 握手的可靠性取决于"页面脚本有没有跑到那一行"。页面脚本一抛异常，握手永远不来，表现是**双击毫无反应**——一个完全静默、还很难查的失败。
  - `did-finish-load` 是宿主自己管的，页面再烂也会触发。
- 顺带删掉了 preload 的 `ready()`、渲染层的 `ready()` 调用、主进程的 `letter:ready` 处理——**换机制就要把旧机制的残骸清掉**，不然下一个人会以为两套都在用。
- **教训**：握手是为了解决"谁先谁后"，如果宿主本来就有"我准备好了"的事件，就没有"谁先谁后"的问题。

## 2026-10-28 · 为了"可测"而牺牲真实体验，是最容易通过评审的那种错

- **现象**：给 `theme.json.timings` 加 SleepAfterMs 时，为了让"主题里确实有个值"好看，给 ragdoll 写了 `sleepAfterMs: 20000`（内置默认是 60 秒）。用户第二天就报：**"working 的过程中不知道什么时候就睡觉了，然后又敲键盘，然后又睡觉"**。
- **两个错叠在一起**：
  1. **口径本身就错**：判定写的是 `now - lastAt > sleepAfterMs`（多久没收到事件），而不是"idle 多久"。一次跑 40 秒的构建期间没有任何事件，于是"没消息"被当成了"没在干活"。
  2. **20 秒太短**，而且**我的回归根本不需要它**——SleepAfterMs 的断言是纯逻辑层的（`getTimings: () => ({sleepAfterMs: 60})`），跟主题文件里写多少毫不相干。我是为一个不存在的理由改坏了真实体验。
- **改法**：判定改成 `s.state === "idle" && now - s.stateSince > sleepAfterMs()`，只从 idle 累计；主题里那个 20 秒直接删掉，回到内置 60 秒。
- **教训**：**把一个真实参数为"方便验证"调小，等于把测试环境的行为搬进了生产**。真需要短工期，就在 Node 侧构造，别改主题资产。这也是硬约束那条"改 CRITICAL 参数必须 PM 确认"的日常版本——用户才是那个每天陪着它的人。

- 用户说了三条现象。第二条（工作中睡着）一查就是**我前一天改出来的**，不是"新发现的需求"。

## 2026-10-28 · 删主题可以，别顺手把防线一起删了

- **现象**：用户说「crab 也可以删掉了，暂时不需要更多的主题」。删完发现回归里四处依赖它：「看板列出了主题」要比对 `crab,ragdoll`、「切主题后立刻换形象」要切到 `crab`、帧数要比 19、**timings 的对照组**用的也是 crab（它没写 `timings`）。
- **最省事的三种做法全是错的**：把断言一起删（防线没了）、把期望值改成单主题（那条断言从此永远为真——`ok==="ragdoll"` 是恒真的，因为只剩一个）、或者偷偷留着 crab（违背用户要求且是同一类谎言）。
- **做法**：回归运行时往 `themes/` 临时写一个 `probe` 主题（帧序列、多帧、带 `variants`、`finally` 里删掉）。它能被运行时看见，是因为 `listThemeIds()` 每次都 `readdirSync`——不像 `THEMES_DIR` 那样只在模块加载时算一次。**删资产不能把"这个功能还活着"的证据一起删掉，要换个证据。**
- **顺手赚到的**：probe 没有 `rigType`，正好是帧序列主题——crab 删掉之后帧序列这条路径本来会失去端到端覆盖，现在被 probe 接住了。删一个东西之前先问：**它在测试里除了"当主题"还扮演了什么角色**。

## 2026-10-28 · 有一段代码跑了很久才知道它一直是坏的

- **现象**：盘点时发现 `verify-electron.js` 里有两处在调用 `window.petDebug.motion()`。那个出口上一轮就已经删了（motion 引擎随骨骼重写一起没了）。**调用它会直接 TypeError。**
- **为什么一直没炸**：两处都在 `if (rigMode) … else …` 的帧序列分支里，而默认主题 ragdoll 是骨骼路径，`else` 从来没被执行过。它们测的"眼睛被压扁"也是 motion 引擎的能力，早就没了。
- **教训**：**一个分支如果永远不进，它里面的代码是不会被"验证不通过"的**——它既不会被 QA 打到，也不会报错，只会安静地烂掉。所以判定要不要留一段"另一条路径的处理"，不能因为它在报告里从没红过。要么让它真的跑起来（这次用 probe 主题跑到了），要么删掉。
- 盘点方法：**逐个 grep `petDebug.<name>` 的调用点，再看每个调用有没有对应的 `ok()`**。只统计"出口有几个"会漏掉"出口是死的"这种情况。

## 2026-10-28 · 「下一个」和「当前」差一格，是最难看出来的 bug

- **现象**：做表情变体，`variantCursor[state]` 存的是"下一次要用的槽位"（写的时候顺手，因为取完就自增最省一行）。于是 `petDebug.variant()` 报的 `pick` 比屏幕上实际在播的超前一格——看起来像"它说切到变体了，画面还是主资产"。
- **修**：cursor 存**当前选中**的槽位，`undefined` 表示还没进来过（于是第一次播的一定是主资产）。
- **同类**：同一批失败里还有一条是探针 `querySelector('svg.frame.on')` 没限定 `.layer.show` ——双图层交叉淡入时**旧图层的帧还要挂 240ms 才清**，不限定就会抓到正在淡出的那一套，读出来的是"上一套"的颜色。凡是" getCurrent 画面上的东西"，先问**它在哪个图层/哪个容器**。

## 2026-10-28 · 搬一个配置项之前，先确认它有没有消费者

- **现象**：台账挂了很久一条待办——「状态时长（25s 发呆 / 60s 入睡）仍写死在 `state.js`，没进 `theme.json`」。照着做，打开 `state.js` 一看：那个 `IDLE_AFTER_MS = 25_000` **从头到尾没有任何消费者**，旁边那行注释自己就写着「目前没有被任何逻辑使用」。
- **这条待办是错的**：它把"代码里有个常量"当成了"这是个配置项"。25 秒发呆这件事从来没有发生过，只是有人想过。**台账也会记错，而且错得很有说服力**——它带着具体数字，读起来像实测。
- **差点犯的错**：如果顺手把它一起搬进 `theme.json.timings`，就是硬约束 25 刚立的那个事故——主题作者写了 `idleAfterMs`，校验通过、加载成功、什么都不发生。**规矩立完不到一小时，最容易在自己手上破。**
- **判据没变**：这个字段有消费者吗。没有 → 不搬，删掉，把它那个没解决的问题留进注释（长工具调用跑 40 秒期间没有任何事件，会被误判成闲置——真要做，先回答这个）。
- **真正搬的是** `ONESHOT` 三个时长 + `SLEEP_AFTER_MS`，因为它们每 250ms 都在被 `tick()` 读。**搬之前先 grep 一遍引用数**，比读注释可靠。

## 2026-10-28 · 新断言要有对照组，否则它可能一直在测别的东西

- **现象**：给 `timings` 写断言，第一版只测了「主题写 60ms → 220ms 后退回 idle」。过了。但这个断言**换个实现也能过**：万一 attention 本来就只有 60ms 呢？万一 `getTimings` 根本没接上、只是默认值碰巧很短呢？
- **修法**：每条都配一个**对照组**——`getTimings: () => null` 时，220ms 后必须**仍在** attention（默认 2400）、仍是 working（默认 60 秒）。两组一起过，才证明「差别来自主题写的那个值」。
- **同一个道理的另一面**：`timings` 没写时，`theme.js` 返回 `null` 而不是编一份默认。**默认值的真相只能有一份**（在 `state.js`），两边各存一套时，分叉是静默的——你会看到"主题 A 睡得快、主题 B 睡得慢"，查半天。所以「没写就读作 null」本身也有一条断言。
- **还挡了一条**：主题只能在 `ONESHOT` 已有的三个键上改时长，给 `working` 写时长也不能把它变成 oneshot。否则一个主题就能让「工作中」播 2 秒就消失——**那是改状态机的形状，不是改外观**，而且改完是静默的。

## 2026-10-28 · 台账里的数字，得是跑出来的那个数

- **现象**：台账四处写着「回归 103/103 全绿」。跑出来是 **102 PASS / 0 FAIL**。差的那条是「剪贴板拿到的是完整路径」。
- **它不是失败**：那段逻辑先重试 6 次读剪贴板，读不到就写一次 `PROBE-OK` 再读回来做能力探测；**探测也失败才走 `[warn]` 跳过**——这是为「CI 里没有剪贴板」设计的降级，既不 PASS 也不 FAIL。
- **为什么会写错**：103 是**声明**的断言条数，102 是这次**实际报到**的条数。写台账的时候顺手把「声明数」当成了「通过数」，还配了个「全绿」——**「全绿」这个词最危险，它听起来像"每一条都验过了"，实际是"没有一条报 FAIL"**，而走 warn 的那条根本没验。
- **教训**：台账里的数字必须是**上一次真跑出来的数字**，而且要连同降级路径一起写清楚。否则下一个人看到 103 全绿，会以为剪贴板那条也验过了——这就是同一个「假绿灯」换了件衣服。
- **同类**：上面「永远为真的断言」是**判据**上的假绿灯；这条是**统计口径**上的假绿灯。共同点是：都能在报告里混过去，都不需要撒谎，只要不细看。

## 2026-10-28 · 功能下线时，删掉"消费者"是不够的

- **现象**：用户说「还是不要摸鱼了，改为敲打键盘」。这是把上一轮刚做完的钓鱼彩蛋整个否掉。删干净 `renderer.js` 里的彩蛋引擎和两个部件，十分钟的事。
- **但删完之后**：`src/theme.js` 里还留着 150 行 `normalizeMotion` / `normalizeGags` 校验器，`themes/README.md` 里还写着完整的 `gags` schema（含示例 JSON、字段表、"三条容易踩的"）。**主题作者照着写，会校验通过、加载成功、什么都不发生。**
- **为什么这比留着代码更糟**：留一段没人调的代码，至少 grep 得到、读代码能看见"这里没人用"。留一个**活的校验器**，它会在加载日志里给你一个"嗯，这个主题没问题"的信号——一个假的绿灯。
- **判据只有一个**：这个字段还有消费者吗。没有，就连校验、文档、回归断言一起删。
- **同类**：回归里那条「motion 声明的部件在 SVG 里都存在」——`def.motion` 永远是 `undefined`，`for` 循环一次都不进，**断言永远为真**。它每个月都在报告里 PASS，长得像一道防线。删掉它的时候我犹豫了一下（"以后恢复 motion 不就用上了"），答案是恢复的时候再写。

**顺带踩到的一个真漏洞**：`src/renderer.js` 里有一行 `this.rootLayer.innerHTML = createRiggedRagdollSVG()`，**违反硬约束 19**（`src/` 下 innerHTML 必须为 0），而且活了整整一轮。它不报错、不崩、画面正常，因为模板是我们自己的字符串——于是所有人都觉得它"不算"。可那条约束本来就是为了防"下一次 `innerHTML` 里出现外部数据"。**写在台账里的规则，如果没有人执行，它的状态永远是"未知"而不是"满足"。** 现在它是一条扫文件的断言了。

## 2026-10-28 · 「有这个出口」和「这个出口有货」是两件事

- **现象**：回归救到 104/105，最后一条「弹簧通道都建起来了（≥20 个）」报**通道 0 个**。rig 里明明有 28 个 `SpringChannel`，不可能没有。
- **原因**：`petDebug.springs()` 里写的是 `ragdollRig.springs`，而 rig 构造时写的是 `this.sp = { … }`。名字对不上，`if (!…) return {}` 干干净净地返回空对象。
- **为什么不早发现**：返回值是 `{}` 而不是 `undefined`，更不是抛错。调用方（回归）拿到空对象后自己就判断通过了——我们这条新断言拿到 `{}` 才算失败。**在写这条断言之前，它沉默了整整一轮。**
- **教训**：这是同类事故的第四次（前三次：CSP、白名单不在路径上、`VISUAL_STATES` 消失）。前三次还能被回归数量提醒，因为一坏就坏一大片；这种「单点接错」的只有**主动为它写一条自检**才会暴露。所以硬约束加了一条：**`petDebug` 的每个出口要么删掉，要么有一条断言证明它返回的是真东西**（不是 `{}` / `null` / `[]`）。

**顺带一条关于查错顺序的**：这条断言本来是我为了让「28 个通道」这个说法有个依据才加的，结果它立刻揪出一个真 bug。**断言的价值常常不在它守的东西，而在逼你先把基数读出来**——「理应是多少」这个问题一旦提出，`0` 就藏不住了。

## 2026-10-28 · 探针要选「每帧从零算出来的量」，不是「会收敛到定值的量」

- **现象**：想证明「骨头版也在动」，于是连续 12 次读 `petDebug.springs()`——12 次快照**一模一样**，判成没在动。而同一时刻猫明明在呼吸。
- **原因**：弹簧的**目的**就是收敛到目标值。working 是个稳态，进入 1 秒后所有通道都到位了，读数当然不再变。**拿一个"追求不变"的量去证明"在变"，逻辑上是反的。**
- **修法**：改读每帧由正弦直接推导、不经弹簧的那几个 transform（`rig-body-group` 的位移含 `breathSin`、`rig-ruff` 的缩放含 `breathCos`、尾巴的 `d` 每帧重算），实测 12/12 全不相同。
- **教训**：写「XX 在动」这类断言前先问一句「这个量稳态时会不会停在某个值上」。会停的量只能用来测**过渡**（切换、收敛），不能用来测**持续**。

## 2026-10-28 · 写进去 `3.80px`，读出来 `3.8px`

- **现象**：断言期望 `translate(3.80px, -2.80px)`，实测稳定读到 `translate(3.8px, -2.8px)`，红得很固执。
- **原因**：我们是 `el.style.transform = "…px"` 写进去的，再经 CSSOM 读回来时**已被重新序列化**——尾零按 CSS 数值规范被去掉。`toFixed(2)` 只是决定了「写的时候保留两位」，管不了浏览器怎么串回来。
- **修法**：判据改成**数值 + 容差**（两个分量各自差 0.06 以内就算到），不再比字符串。
- **教训**：凡是经过 Web API 序列化回来的值（CSSOM、`getBoundingClientRect`、`JSON.stringify`），期望值一律走数值比较。「写着一模一样的期望却在红」时，先怀疑中间层把值改写过，而不是怀疑断言写错了。

**同为这一类**：替换代码块时用一个「区块内部也会出现」的字符串当终点锚点（`index('…')`），命中了更早的那一次，切片过短，新旧代码块叠在一起 → `Identifier 'gagA' has already been declared`。**终点锚点必须选在区块之后**，或者干脆按行号切片。

## 2026-10-28 · 重写最容易丢的不是功能，是那两道「没用的闸」

- **现象**：用户拿来一版外部重写的渲染层，说「加载失败了」。修完 `schemaVersion` 就通了，画面比以前好看得多、切换也更顺。看起来是一次成功的升级。
- **问题**：这一版同时**删掉了 CSP**、把主题帧的注入口从 `svgNode()` 改成了 `innerHTML = frames.join("")`、删掉了 `window.VISUAL_STATES`。三件事都不报错、不崩、画面正常。
- **为什么会被删**：因为它们当时的**效果**是零。CSP 挡住的东西一个都不在（没有内联脚本、没有远程请求），白名单挡住的东西一个都不在（主题都是自己画的），`VISUAL_STATES` 只是调试用的。**从「今天能不能跑」看，它们全是冗余。**
- **代价**：白名单从「唯一的出口管控」退化成「文件里几个没人调用的函数」。审计时 grep `sanitizeSvg` 会得到「有」，于是防线看起来还在——**留着但不在路径上，比删掉更危险**。
- **教训一**：防线类的代码，评价标准不是「它今天拦住了什么」，而是「明天漏了还剩什么」。这类代码永远通不过「有用性」审查，所以需要一条**可机械检查的硬约束**（`innerHTML` 出现次数 = 0），而不是靠人记得。
- **教训二**：架构重写之后第一件该做的事，是**看回归掉了多少**。这次从 103 掉到 54。掉的 49 条里，38 条是「探针被删」、11 条是「断言假设过时」——但只有逐条看才知道，因为它们在同一个提交里一起变红，看起来像「测试过时了」。

## 2026-10-28 · 同一个字段的第二次死亡

- **现象**：`eyeTracking: false` 又不生效了——猫在那一版里是伏案打字（这一轮已改回水边垂钓），还在追光标。
- **原因**：上一轮刚修过一模一样的 bug（字段被 `theme.js` 校验、被 IPC 传输、渲染层从没读过）。这一版重写新写了 rig 分支，`applyGaze()` 里**无条件** `setGaze()`，老字段没人管。
- **为什么重写必然复发**：重写的人看的是「我要实现什么」，不是「原来那个 if 在守什么」。**新分支默认不继承老字段的语义**，而字段本身不会报错——它只是静静地没人读。
- **修法**：`applyGaze()` 把 `eyeTracking` 提到分支之前，统一算一次 `track`，rig 与帧路径都用它。**开关要先于分支计算**，否则每条新分支都要记得读一次。
- **教训**：声明式字段的「接上了」不是「有代码用到它」，是「**有一条会因它失败的断言**」。这次回归里那条 `working 的 eyeTracking 为 false` 一直红着——它其实一直在报警，只是被「测试过时了」的解释盖过去了。

## 2026-10-28 · 1.8px 的眼睑压不住 28px 的眼睛

- **现象**：给 working 设了 `eyelidTop: 1.8` 做「疲惫半睁」，截图看上去完全正常睁眼。
- **原因**：眼睑是一块从 `y=76` 往下压的矩形，眼球直径 28（`cy=92, r=14`）。压 1.8px 只挡掉 **6%**，肉眼根本分辨不出。要读成「半睁」得压到 11px 左右（约 40%）。
- **为什么写了却看不出**：作者心里的「半睁」是个形容词，落到代码里是绝对值。**形容词和像素之间没有换算表**，只能量：先算出目标部件有多大，再决定参数。这个主题里眼睛 28px、脸 74px、整个 viewBox 200px。
- **教训**：任何「轻微 / 明显 / 半」这类形容词参数，先量基准尺寸再定数值，否则一个数量级的偏差是常态。

## 2026-10-27 · 字段"写了"和字段"接上了"是两件事

- **现象**：给布偶猫的 working 状态写 `"eyeTracking": false`——猫在钓鱼，不该追着光标看。改了，跑起来还在追。
- **真相**：`theme.js` 校验它、状态对象带着它、IPC 送过来了，**渲染层一次都没读过**。`applyGaze()` 只管找 `.pupils`，找到就写 `transform`。这个字段从 S7 起就是死的，只是之前没有哪个状态需要它关。
- **为什么难发现**：它不报错、不警告，甚至"看起来生效过"——因为早期那些状态恰好都写了 `true`，而 `true` 和不看字段的效果一样。**一个永远为真的开关，和一个不存在的开关，运行时完全等价。**
- **修法**：`applyGaze()` 先看 `currentDef.eyeTracking`；同时给 working 补回一个 `.pupils` 组，让这个 `false` **有对象可管**。否则"不跟眼"只是"这张图里恰好没画瞳孔层"——那是巧合，不是功能，下一个人画出瞳孔就会自动失效。
- **教训**：每加一个声明式字段，配一条**能因它失败的断言**。这里的两条：「working 的 eyeTracking 为 false」+「working 下瞳孔不跟鼠标」+「idle 的为 true（对照组）」。没有对照组的那条断言，用"根本没有瞳孔"也能通过。

## 2026-10-27 · 还没到点的那一段，不许先写一遍

- **现象**：彩蛋第一段完全不动。鱼本该从水下浮上来，实测 300ms 时 `transform` 是 `translate(0.00 0.00)`。
- **原因**：`renderGag(t)` 遍历所有步骤，对还没到 `at` 的那一段做了 `clamp((t - at) / span, 0, 1)` = 0，于是**照着 `from` 写了一遍**。而同一部件的后一段 `from` 是 `[0, 0]`，它把正在演的第一段覆盖了。**"最后写的赢"这条规则，让一条没开始的规则赢在了起跑线上。**
- **修法**：`if (t < step.at) continue;`——没开始就不参与。语义随之变成"当前有效的那一段说了算"，也就是人读时间线时的直觉。
- **为什么第一版没测出来**：我测的是"有没有在动"（两次采样不同），而它**确实在动**——动的是第二段。**"在动"和"按预期在动"是两条不同的断言。**
- **教训**：凡是"按时间轴依次应用多条规则"的实现，明确三种状态：未开始 / 进行中 / 已结束。把"未开始"当"已结束"处理，是最常见的静默错误，因为它只影响开头那一小段。

## 2026-10-27 · 收尾要"恢复原值"，不是"设成默认值"

- **现象**：鱼被吃掉之后，猫的**眼睛没了**。
- **原因**：彩蛋收尾对着 `parts` 里的每个部件执行 `setAttribute("display", "none")`。鱼和拖鞋本来就该藏，可 `pupils` 是**本来露着**的——它进 `parts` 只是为了"跟着看一眼鱼"，结果被当成一次性部件一起藏了。
- **修法**：开演前把每个部件的 `{display, transform}` 存一份快照，收尾按快照逐个恢复（原值不存在就 `removeAttribute`）。多一个 Map，换掉一整类 bug。
- **为什么原来那种写法很自然**：因为部件的"常态"在编写时只有一个——藏着。等到第二个用途（"临时接管一个常驻部件"）出现，那个隐含假设就崩了。
- **教训**：**任何"用完还原"的逻辑，还原的目标都必须是快照，不是你以为的默认值。** 同一个部件被不同用途复用时，这一点尤其致命——而且失效方向是"少画一块"，很容易被当成美术出错，而不是逻辑出错。

## 2026-10-27 · 想同时位移和缩放，除了再套一层没有别的办法

- **现象**：鱼被吃掉要靠"往嘴边移动 + 缩小"。写两条规则给同一个 `<g class="m-fish">`，结果只有一条生效。
- **原因**：SVG 元素的 `transform` 是**一个属性**，不是可叠加的样式列表（CSS 的 `transform` 才是列表）。`setAttribute("transform", "translate(a b)")` 会把上一句写进去的 `scale(...)` 直接顶掉。而我们的引擎每帧都在写。
- **修法**：内层再套一个 `<g class="m-fish-in">`，外层管位移、内层管缩放。两个元素各有一个 `transform`，互不覆盖。
- **教训**：这条要提前写进契约（`themes/README.md` 硬契约第 4 条），因为它**失败时不报错**——画面上只是"缩放没生效"或者"位移没生效"，看起来像参数写错了。凡是"一个属性承载全部变换"的图形系统，组合动作都必须靠**嵌套**表达。

## 2026-10-27 · 间歇失败的测试比没有测试更危险

- **现象**：4 次回归有 2 次挂在「换状态时切换图层」，报 `layerB → layerB`。单看这个断言，像渲染层没换层。
- **第一次误判**：怀疑是主题异步到达和测试抢跑，加了"等主题加载"的断言——还是偶发。
- **真正定位靠一行日志**：给 `petDebug` 加了 `stateLog()`（最近 20 次状态推送），失败时打出来：
  `[{t:197,visual:"idle"},{t:309,visual:"idle"}]` —— **两次 idle，间隔 112ms**。
  于是真相是：状态机 tick 的 250ms 周期已经把 `lastVisual` 从 null 推成 idle，300ms 的"首帧保险"又推了一遍；测试恰好在两次之间把状态改成 working，第二次 idle 把它顶回去了。
- **修法**：应用侧去掉重复推送（`pushedAnyState`），测试侧动手前先等推送静默 400ms。
- **顺手加了一条永久断言**：「换一次状态只重建一次」。重建次数翻倍画面上完全看不出来（结果一样），但它是竞态的指纹。
- **教训**：调试"随机失败"时，**不要读代码猜，加观测点**。一行环形缓冲日志的价值超过半小时推理。另外——**别用放宽断言的方式让它变绿**，那等于把 bug 藏起来。

## 2026-10-27 · 安全修复顺手砍掉功能，比漏洞更难发现

- **场景**：S2 审 SEC-09（cwd 泄露）时，修法写的是「cwd 只留 basename」。听上去干净利落，一天之内相安无事。
- **到 S6 才暴露**：看板要做「复制路径」和「跳转终端」，两者都需要完整路径。按原来的修法，功能根本做不出来。
- **关键判断**：这时候有两条路——① 放弃功能，继续只留 basename；② 取消脱敏。两条都错。正确的是**分层**：存储层留完整路径（只活在主进程内存里），快照层只出 basename（会进渲染进程、上屏幕），完整路径唯一的出口是用户显式点击时由主进程单条释放。
- **教训**：「脱敏」的粒度应该按**数据流向**切，不是按字段切。一刀切掉字段，看起来最安全，实际是**把风险转嫁成了功能缺失**——而功能缺失不会出现在安全报告里，所以永远不会被回头修。
- **同类检查项**：以后凡是写「只保留 X」，都问一句「有没有哪条链路必须要完整的 X」。如果有，就得分层，而不是砍掉。

## 2026-10-27 · 测试跑不起来，八成不是代码坏了

- **现象**：改完代码跑 `npm run verify:electron`，报「渲染进程 15s 内没起来」。第一反应是渲染层被我改崩了。

## 2026-10-27 · 一只眼睛不动：`querySelector` 从不告诉你"还有第二个"

- **现象**：换完形象，用户反馈"有一只眼睛不跟着鼠标转"。不报错、不警告、画面看起来只是"有点怪"。
- **原因**：画眼睛时图省事，给左右眼各包了一个 `<g class="pupils">`。而渲染层是 `el.querySelector("svg.on .pupils").setAttribute("transform", …)`——**`querySelector` 只返回第一个匹配**，所以只有左眼转了。右眼不是"没有动效"，它根本收不到任何指令。
- **为什么容易犯**：`class` 在别的框架里常被当成"标记一类元素"用，多份是正常的。但在这里，`pupils` 这个名字承载的是**唯一性语义**（"那个瞳孔层"），DOM 结构必须配合这个语义。命名和结构脱节，是这类 bug 的温床。
- **修法**：两只眼的瞳孔收进同一个组，组内坐标用绝对值（渲染层会整个覆盖 `transform`）。
- **教训**：凡是 `querySelector` + `setAttribute` 这种"拿到就改"的写法，都要问一句「这个东西会不会有多个」。**更要紧的是给它配断言**——回归里现在有「每帧最多一个 `.pupils` 组」和「瞳孔层里两只眼都在」，前者防复发，后者防"合成了一个但漏画一只眼"。

## 2026-10-27 · 预判写错了坐标系，五条要求四条作废

- **场景**：S5 开工前按惯例先写"五条安全要求"，写得很细：一次性 nonce 绑 `session_id` + `tool_use_id`、nonce 只走 stdin、默认 deny、回包要过 Host + token。
- **发现**：全错。写预判时脑子里默认 `PermissionRequest` 和 S4 的观察型 hook 一样是 **command hook**（起个短命进程读 stdin）。去主仓库 `hooks/install.js` 一看，它是 `type: "http"`：**Claude Code 直接 POST 我们的端点，HTTP 响应就是决定**。没有中间进程，没有 stdin。
- **连锁后果**：没有"独立的回包步骤"→ nonce 无从谈起（请求即响应、同一个 socket，决定天然绑在请求上）；没有 stdin → 第 2 条整条作废；调用方是 Claude Code 自己 → 它读不到端点文件，token 根本校不了；默认 deny 是错的 → deny 让工具**静默失败**，用户还以为自己批准过，正确做法是 204 不做决定、回落原生提示。
- **教训**：**预判的价值在于"写下来"，不在于"写对"**。但前提是预判必须在读源码之前标成"假设"，读完源码立刻核对、错了就整条重写而不是打补丁。四条错预判如果只是逐条打补丁，会得到一个"每条都做了点事、但都不对"的实现。
- **顺带学到**：真需要 nonce 的是**远程审批**——决定来自公网、可重放。主仓库的 nonce 只出现在 `telegram-native-runner.js`，`/permission` 那条路径上根本没有。这个区分以后再遇到类似设计时可以直接套。

## 2026-10-27 · 表现为"慢"而不是"错"的 bug 最难发现

- **现象**：启动后的**第一个**权限请求永远不弹内容，气泡空白，点了没反应，2 分钟后静默回落到终端。第二个开始正常。
- **原因**：气泡窗口懒创建。`webContents.send` 发出去的时候，渲染层还没执行到 `bubbleRenderer` 的监听注册，这条 IPC 被**静默丢弃**——不报错、不排队、不重试。Electron 的 IPC 就是这样，发早了就是没了。
- **修法**：握手。渲染层注册完监听后回一个 `bubble:ready`，主进程在此之前用 `bubblePendingEntry` 暂存，收到握手才真正投递。
- **为什么难发现**：它不崩、不报错、日志干净。用户看到的是"有点慢"，开发者会归因到网络、到 hook 超时、到系统负载，就是不会想到"消息发早了"。**这类 bug 只有断言能抓**——回归里那句「气泡显示了工具名」就是为它写的。
- **推广**：凡是"主进程推、渲染层收"的链路，只要渲染层是懒创建的，第一次投递就必须有握手。这和 S1 主窗口不一样——主窗口 `ready-to-show` 之后才 show，天然避开了。

## 2026-10-27 · 退出时的收尾不是洁癖，是 10 分钟的卡死

- **场景**：用户关掉桌宠的瞬间，Claude Code 可能正卡在一个 `PermissionRequest` 上等回应。
- **如果不管**：那条 HTTP 连接既不断开也不答复，一直悬着。hook 侧写的是 `timeout: 600`，所以终端最长 **10 分钟没有任何反应**，而气泡已经不在了，用户完全无从判断发生了什么。
- **做法**：`before-quit` 里 `permissions.dispose()`，把仍 pending 的请求全部以 204 结束。204 让 Claude Code 立刻回落原生提示，用户切到终端照样能批。
- **容易写错的地方**：`dispose()` 走 `settle() → onResolve()`，而 `onResolve` 里有"弹下一条"的逻辑。写得不对就会在退出过程中新建一个浏览器窗口，或者把排队项漏成悬空连接。所以回归里**同时挂两条**（一条在显示、一条在排队）来覆盖，只测一条测不出来。
- **教训**：任何"资源在退出时释放"的逻辑，都要问一句「如果还有人在等这个资源呢」。`server.close()` 等的是连接，而连接的对端是一个真实在等的进程。

## 2026-10-26 · Electron 的安全默认值是"半个"默认值

- **场景**：给 S1-S3 做安全审计，本以为 `contextIsolation: true` + `nodeIntegration: false` 就基本安全了。
- **发现**：这两个确实是关键项，项目里也都写对了。但 Electron 的安全面远不止这两条——`sandbox` 依赖版本默认、`webSecurity` 没写、`index.html` 没有任何 CSP。三个都没配，等于「门锁好了但窗户开着」。

- **教训**：桌面应用的威胁模型和 Web 不一样。Web 里"跨域被拦"是一种保护；桌面端本地端口是**没有同源策略**的，必须自己补 Host/Origin/Token 三件套。

## 2026-10-27 · 同一套判据写在两个脚本里，只改了一个

- **现象**：S7 收工终检，`check-filemap.js` 报 `[ok] 台账与文件系统一致`，`daily-check.js` 同时报「FILE_MAP 漏记 43 个文件」并 exit 2。两份脚本判的是同一件事。

## 2026-10-27 · 断言被测对象被环境反过来改掉了

- **现象**：「gaze 收敛到满幅位移」偶发失败，读到的值是 `translate(-0.98 0.81)`。看起来像"插值没收敛"，但又是个合理坐标，不像坏了。
- **原因**：主进程每 100ms 按真实光标位置推一次 `gaze`。测试注入 `{x:1,y:-1}` 之后，一条真实推送到达，把目标覆盖成光标位置；渲染层老老实实插值到光标——**它的行为完全正确**，错的是断言的前提（"注入的值会一直有效"）。
- **为什么费时间**：失败信息长得像 bug（一个不是期望值的坐标），实际是"收敛到了别的地方"。这类假失败最误导，因为被观测的那段代码根本没坏。
- **修法**：`petDebug.gaze(g, pin)` 加钉子，pin 期间忽略真实推送，断言完 `unpinGaze()`。
- **教训**：凡是「注入一个值 → 等它生效」的断言，动笔前先问一句：**还有谁会写这个值？** 只要有第二个写入方，就必须能独占，否则断言就是在赌时序。

## 2026-10-27 · 放宽容差别放成空壳

- **背景**：透明检测被背景噪声干扰（用户自己开着一只桌宠压在同一位置）。
- **第一版修法**：容差改成「背景噪声 + 2」。数字上很合理，也确实让断言稳定通过了。
- **问题**：实测出现 `noise=137, diff=137` 的角——那一块桌面本身就在剧烈变化，`137 <= 137+2` 成立，于是"通过"。可这个角**什么都没测到**。一条会自己静音的断言，比没有这条断言更糟：它让人以为检查过了。
- **修法**：噪声超过阈值（6）的角**不参与判定**，并要求至少 3 个可用角；可用角不足就打「跳过」而不是「通过」。
- **教训**：**容差一旦随环境浮动，就必须同时约束"可判定的样本数"**，否则容差会一路涨到断言失去意义。

## 2026-10-27 · "卡顿"不是帧率不够，是采样方式错了

- **用户原话**："每个动作切换也不丝滑，都是卡顿式切换。"
- **第一反应（错的）**：把 fps 从 8 调到 12、24。没用的，因为病根不是"帧不够多"。
- **真正的原因**：帧是**离散**替换的。8fps 意味着每 125ms 画面完全重画一次，中间 125ms 一动不动。
  人眼对这种"定住—跳变"极其敏感，再多几帧也还是同一个病——它长得像频闪，不像动作。
- **修法**：把动画从"换图"换成"改参数"。部件（身体/头/尾巴/眼睛）的位置每帧算一次，
  60fps 连续变化。同一个姿势图，靠插值就能呼吸、摆尾、歪头、眨眼。
- **教训**：判断"是不是动画问题"要看**时间的连续性**，不是看帧数。
  离散采样再密也有台阶；连续函数才没有。这条判断之后，`frames` 从 19 张降到 7 张，
  反而更丝滑——**帧数和流畅度根本不是一回事**。

## 2026-10-27 · 被白名单逼出来的架构，比原方案更干净

- 白名单拒 `<style>` 和 SMIL，主题里写不了 CSS 动画。当下的感觉是"限制碍事"。
- 但顺着这条限制走，动画只能放在渲染层：主题声明**意图**（哪个部件、怎么动、多快），
  计算全在我们自己的代码里。结果比"主题自带一段 CSS"好得多——CSS 是不可审查的，
  `motion` 是数据，能校验、能钳制、能测试。
- **教训**：安全限制常常把设计推向"数据和执行分离"这个更结实的位置。
  先问"这条限制逼我改什么结构"，而不是"怎么绕过它"。

## 2026-10-27 · 需要镜像的形状，别手算坐标

- **现象**：新画的猫耳朵变成了两根细天线。
- **原因**：左右耳用绝对坐标各算一次贝塞尔控制点，右边那组算错了（符号写反），
  结果就是两条细线。
- **修法**：只在局部坐标里画**一只**耳朵（宽 32、高 40、向上），再用
  `translate(...) rotate(...) scale(±1, 1)` 贴到头的两侧。镜像由矩阵负责，不由我负责。
- **教训**：凡是成对出现、只差一个镜像的东西，都该写成"一份形状 + 一次镜像变换"。
  手算两份坐标，等于给自己留一个必然发生的符号错误。

## 2026-10-27 · CDP 的 5 秒超时会把长断言变成"undefined"

- **现象**：新加的眨眼断言输出 `最小纵向比例 undefined`，但没有抛异常、也没有报错。
- **原因**：`R.eval` 底层 `send()` 有 **5000ms 超时**，超时后返回 `{error:{message:"timeout"}}`，
  `eval` 把它转成 `undefined`。而眨眼采样要在页面里跑 88×60ms ≈ 5.3s——刚好越界。
- **修法**：长采样不要写成"页面里的一个长循环"，改成**从 Node 侧逐次读**，
  每次 eval 都远小于超时窗口。
- **教训**：断言里的等待时间一旦超过工具链的默认超时，失败信息会变成 `undefined` 这种
  毫无指向性的东西。写采样型断言前，先确认"一次调用最多能跑多久"。

## 摘自 README 的踩坑（原记录在项目 README，此处存档备查）

### `TypeError: Cannot read properties of undefined (reading 'whenReady')`

- **现象**：`electron .` 启动即崩，`require('electron')` 拿到的是路径字符串而不是 API 对象。
- **原因**：环境里存在 `ELECTRON_RUN_AS_NODE=1`（某些 IDE、CI 或别的工具设置过），Electron 退化成纯 Node 进程。
- **排查**：`env | grep ELECTRON`
- **绕过**：`env -u ELECTRON_RUN_AS_NODE npm start`（PowerShell：`$env:ELECTRON_RUN_AS_NODE=""; npm start`）

### 窗口全黑 / 出现灰色方块

- **原因**：`transparent: true` 必须同时配 `backgroundColor: '#00000000'` 和 `hasShadow: false`。
- **教训**：三个参数缺一个就露底色，这是 Electron 透明窗口的固定组合，不是可选项。

### 点不到、也拖不动

- **原因**：`setIgnoreMouseEvents(true, { forward: true })` 之后窗口默认不接收点击，只转发 `mousemove`。
- **解法**：必须在检测到鼠标压在宠物身上时显式调 `setIgnoreMouseEvents(false)` 切回来。
- **衍生坑**：窗口跟着光标移动后，光标在窗口内的相对位置不变，renderer 就再也收不到 `mousemove`——所以拖拽只能用主进程 `screen.getCursorScreenPoint()` 轮询，不能用 `-webkit-app-region: drag`。
