## 2026-11-10 · 分组只解决"混在一起"，没解决"一屏全是历史"

**场景**：用户原话「现在的 clawd 会话，太乱了。目前接入的是 workbuddy 以及 deep seek
harness 两个。deepseek harness 是有 sessions 概念的……workbuddy 参考 deepseek harness
看看能不能找到类似的」。

"太乱"是个很模糊的抱怨，先得把它拆成可修的东西。真机上一看，乱有两层：

1. **两家混在一个平铺列表里**，而它们**能不能说话**完全不一样——DSH 的会话点「说一句」
   真能往里发，WorkBuddy 的点了没反应。同一种卡片、两种含义。
2. **一屏全是历史**。DSH 那组一开就是 **46 条**，WorkBuddy 12 条，聚合成 "58 条 ·
   累计出 245k token"。用户想找"我正在用的那条"要在里面捞。

**只做第 1 层是不够的**，这是我这一轮最实在的收获：分组把"不同种类"分开了，
但组的**大小**没变。一个折叠了两层、每组还是 46 条的列表，读起来和 46 条平铺没区别——
它只是把混乱装进了文件夹。所以真正的修法是两件一起做：**先分组（种类）**，
**再默认只列最近 8 条 + 一行「还有 N 条（展开）」（体量）**。第二件比第一件便宜得多，
效果却更大：那一屏从"46 条历史"变成"8 条最近 + 3 个组头"。

### 那个"看看能不能找到类似的"，答案是能找到，而且形状几乎一样

WorkBuddy 和 Claude Code 都把会话落成 `<家目录>/.<product>/projects/<项目 slug>/<uuid>.jsonl`，
一行一个 JSON。WorkBuddy 是 `{type:"message", role, content:[{type:"input_text"|"output_text"}], cwd, timestamp}`，
Claude 是 `{type: "user"|"assistant", message:{role, content:[{type:"text"}]}}`——
**同一份抽象，两种皮**。写个 `message_of()` 归一成 `(role, blocks)` 就都通了。

以前看板只看 hook 事件，而状态机里的会话十几分钟就过期，所以 WorkBuddy 在看板上
**永远只有"正在跑的那一条"**。用户说"接入的是两个平台"，看到的是一个平台一堆、
另一个平台一条——这本身就是"乱"的一部分：**不对称**。

**但它不能对话。** 查遍 `PATH` 和 `~/.workbuddy/binaries`，本机没有任何
`workbuddy` / `codebuddy` / `claude` CLI。DSH 有 `headless --session-id` 这个一等公民
入口，WorkBuddy 没有。所以这两家的会话**只能看**。

这里有个产品判断：**"只能看"必须由界面说出来，不能让用户试点出来。**
S12-1 刚花了一整轮修"点了允许没有任何返回"，那是同一类病——按钮亮着、点下去没反应，
用户不会认为是"不支持"，会认为是"坏了"。所以组头上直接写「只能看」，组内卡片的
「说一句」`disabled` 掉。`can_say` 是**事实字段**（`agent_preset.is_none()`），不是开关。

### 平台名：唯一的错法是"从来没打算知道"

`clawd-hook.js` 里写着 `agent: "claude-code"`。这不是"猜错了"——是它**根本没打算知道**：
同一个脚本被多个平台调起来，运行时它只看得见"有人给了我一个 stdin JSON"，看不见调用者。

唯一确知的时刻是**安装那一刻**：`install.js` 正在往某个平台的 `settings.json` 里写命令，
它当然知道自己在为谁装。所以把归属**烘进命令行**（`--from workbuddy`），hook 端读回来
（`argValue("--from")`，缺省仍 `claude-code` 保持老行为）。这条后来成了硬约束 54。

配套那一半同样重要：**允许被纠正**。老装法的 hook 会一直报 `claude-code`，
如果新事件到达时坚持"第一次定了就不许改"（`if s.agent.is_empty()`），那条会话
在它出现的第一秒就被钉进错误分组，**重装也救不回来**。所以写的是
`if agent != UNKNOWN_AGENT { s.agent = agent }`——`unknown` 可以被覆盖，已知的名字
也能被更可靠的来源覆盖。三行代码的差别，决定了"重跑一次 install 就好"还是"清库重来"。

### WorkBuddy 把系统提示塞进了 user 消息里

第一版扫出来的卡片，**每一条标题都是同一段话**：「You are WorkBuddy, a highly capable
agentic coding assistant…」。查下来：它把整套系统提示 + IDE 上下文（实测 **9000+ 字符**）
塞在同一条 user 消息的最前面，真实提问裹在 `<user_query>` 里。

不挖这个标签，看板的"标题"就退化成"系统提示第一行"——**50 条会话长得一模一样**。
这让我意识到一件事：用户说"乱"的时候，可能指的不是排版，是**认不出哪条是哪条**。

顺带一条：工具结果也以 `user` 身份回灌。第一版把工具结果也算进"轮数"，
一条跑了二十次 bash 的会话显示"23 轮"，而用户只问了 3 句。判据改成"这条 user 消息
里有没有真正的提问"（有 `input_text` 块且非空）才算一轮。

### 两个闸门当场抓出来的错

`li.more`（「还有 N 条（展开）」那一行）第一版是常驻 DOM、用 `hidden` 藏。
闸门那条断言是 `document.querySelectorAll('#groups .group[data-agent=X] li:not(.more)')`——
我一开始忘了排除 `.more`，结果"这组有几张卡片"把占位行也数进去了，`cards:2` 当场红。
改成 `g.more.remove()` 之后不必再排除：**不存在的东西数不出来**。顺带发现去掉
`more.hidden = true` 那个初值也是必须的——`remove()` 过的节点重新 `append` 时，
`hidden` 还是 `true`，那一行会永远不显示。

另一件：`join()` 里 `agent` 该信谁。DSH 的会话在**两个数据源里都有**——状态机那份
可能被老装法的 hook 写成了 `claude-code`，磁盘那份由文件路径决定、不会错。
所以 `String((r && r.agent) || s.agent || "unknown")`，**磁盘优先**。这类"两个来源
说同一件事、可能不一致"的地方，判据要问"哪一份是它的**出处**"，不是"哪一份更新"。

**一句话**：分清"种类"和"体量"是两个问题；能说与不能说要在同一屏上说清；
归属要在确知的那一刻写下来，并且留着被纠正的余地。

## 2026-11-10 · 判据松的代价，不是"找不到"，是"找错了"

**场景**：用户报「返回找不到 dsh（PATH 里没有 `@//deepseek-ai/dsh`）」。

报错文案本身是`找不到 dsh（PATH 里没有 @deepseek-ai/dsh）`，用户转述时多打了个斜杠，
不是拼接 bug。真正的毛病在**定位范围**：`locate()` 只会扫 `PATH` 上每个目录的
`node_modules/@deepseek-ai/dsh/lib/bin.js`，而本机那份 npm 安装**已经跟着 `C:\nvm4w`
一起没了**——`ls -la /c/nvm4w` 只剩 `.` 和 `..`，`which dsh` 空。

dsh 并没有消失，它活在桌面版里：`AppData\Local\Programs\DeepSeek Harness`。
桌面版的 `resources/runtime/cli/bin/dsh.cmd` 指向
`app.asar/dsh/node_modules/@deepseek-ai/dsh-desktop-host/lib/cli.js`，用
`DeepSeek Harness.exe` + `ELECTRON_RUN_AS_NODE=1` + `--expose-internals` 跑。
拿 `--help` 逐条核过：`--profile headless`、`--json`、`--session-id`、`-` 全在，
`--dump-config` 也能吐出 `cmg · DeepSeek-V4.1-Flash-1017`。**同一个产品，同一套参数**，
只是入口长得不一样。

于是给 `locate()` 加了第二条来源。**然后踩到了这一轮真正值得记的坑：**

第一版判据是"目录里有 `resources/app.asar` 就算桌面版"。写个临时探针跑一下，它选中的是：

```text
node: "C:\Users\Think\AppData\Local\Programs\Cherry Studio\Cherry Studio.exe"
```

`%LOCALAPPDATA%\Programs` 下有一堆 Electron 应用，我只用了一条对**所有 Electron 应用**
都成立的判据，于是"找 dsh"变成了"找一个 Electron 应用"。后果不是找不到——是
**拿 Cherry Studio 的 exe 去跑 dsh 的脚本**，而它还被设了 `ELECTRON_RUN_AS_NODE=1`，
真会以 node 身份执行我们拼的那串参数。这种失败有一整套"看起来在工作"的表现，
比"找不到 dsh"难查一个数量级。

**原因**：判据写的是"像不像一类东西"（Electron 应用），而要问的是"是不是**这一个**东西"。
前者能覆盖全部候选，也能覆盖全部干扰项。

**解法**：两条同时成立才认——`resources/app.asar` 在，**且** exe 名或目录名含 `deepseek`。
名字被彻底改掉的情况用 `CLAWD_DSH_ROOT` 显式指定，**不让"猜"成为默认路径**。
把这次误判钉成回归测试 `does_not_mistake_another_electron_app_for_dsh`。

**教训**：

- **判据的失败有两种，我一直只防了前一种**。「找不到」是显式失败，看得见、能报错；
  「找错了」是静默的，而且它会**继续往下走**——起进程、拼参数、执行。自动发现本机某个
  程序时，判据必须能**排除同类应用**，不是"能被它认出来的都是它"。
- **临时探针的价值就在这里**。单元测试全绿（`desktop_install_yields_a_launcher` 用一个
  干净的假目录，当然绿），因为假目录里没有 Cherry Studio。**只有拿真实环境跑一次**，
  才会遇到"干扰项"这个东西。凡是"扫某个系统目录"的代码，验收必须含一次真机扫描。
- **报错要说"我在哪儿找过"**。`找不到 dsh` 等于让用户去猜；把候选目录打进 stderr，
  下次遇到会自己说话。
- 一条附带的产品判断：桌面版的入口是 **asar 内部路径**，磁盘上查不到（只能由 Electron
  解析），所以这段代码永远没法"先验证再使用"。那就接受它、并且**把它的失败翻译清楚**——
  `Cannot find module` → 「桌面版里的 dsh 入口和预期不一样（可能刚升级过）」。

## 2026-11-10 · 功能通了，不等于用户看见了

**场景**：用户说「通过桌宠发送了一条消息，但任何地方都看不到返回内容」。

第一反应是去查发送链路——`say.rs`、dsh、凭据、管道。但链路是通的：日志里明明白白
`[say] 收工 ok=true reply=收到`。**数据一直在，只是没有一处界面显示它。**

顺一遍才看清这条设计上的漏：

1. 发送成功 → 输入窗 420ms 后自动关掉（当时的理由是"说完就走了，别挡着猫"）；
2. 回复走 `say:done` 事件，只有**看板**在听；
3. 看板默认是关着的。

于是"发一句话"的完整结局是：窗一闪、消失、世界安静。用户唯一能获得的反馈，
是去打开另一个窗口看记录——而这不在他的心智模型里。

**教训**：

- **验收要按用户的视线走一遍**。我的 e2e 盯着 `say:done` 的 payload 断言"reply 有值"，
  这证明的是链路，不是**可见性**。功能通不通和用户看不看得见，是两道独立的问题。
- **"说完就关"是个想当然的默认**。它成立的前提是"用户不需要结果"，而发消息这个动作
  的目的**就是**要结果。凡是"动作的产出就是用户目的"的界面，产出没落地之前不许收摊。
- 顺手补的一条：窗会被复用，迟到的结局必须对号（比对自己发出去的那句原文），
  否则用户关窗重开写第二句话时，第一句的答案会写在第二句下面。

## 2026-11-06 · 一扇「点得动、但没有人接」的窗

**场景**：用户报「确认操作，没有任何返回」——权限气泡上点了「允许」，agent 那边一直没动静。

真实的失败长这样（用 CDP 复刻，时间线是实测的）：

```text
[4] 第二条请求渲染出来：tool=Read，按钮是亮的
[4] 点击允许 @ 702ms
[5] 回包：204，耗时 120003ms          ← 决定根本没发出去，等满了 2 分钟超时回落
[6] 点后页面：note="这条请求已经结束了，等下一个请求吧"
```

**三个入口全都是"界面有按钮，宿主那边没有账"**：

1. `bubble.html` 里那张卡片**加载即可见**，按钮初始是可点的。`permission:request`
   还没到（首次请求、页面重载、事件没投递）时点下去，会撞上
   `if (currentId === null) return;` —— 静默 return，一个字节都不发。
2. `decide()` 先把 `currentId = null`、按钮置灰，再 fire-and-forget 发出去。
   主进程回 `false`（这条请求已经超时/被结掉）时没人接这个 false：卡片留着、
   按钮永久灰，这扇窗从此废掉。
3. 我修 1、2 时引入了一个更隐蔽的竞态：`await` 回执之后再无条件
   `currentId = null`。等回执的几百毫秒里下一条请求已经渲染上来了，
   这行代码把**新**请求的 id 擦掉 —— 卡片显示着 Read、按钮亮着，
   点下去走"没有当前请求"分支。**修 bug 的一行代码自己成了下一个 bug。**

**这一轮真正学到的东西**：

- "点不动"和"点了没反应"是两种病，但用户看到的是同一件事。凡是用户可点的东西，
  必须能回答两个问题：**我这一下发给谁了**、**对方收没收到**。
  `send()`（发完不管）配上"先清状态再发"，等于把所有失败都翻译成沉默。
- 状态清理要**比对身份**，不要无条件写：`if (currentId !== id) return;`。
  这和数据库里的乐观并发是同一件事——异步回来时，世界已经变了。
- 验收脚本也会骗人：第一版断言写成"点完再点一次，卡片应说明情况"，
  但点完之后按钮本来就是灰的，`element.click()` 对 disabled 按钮不触发任何事件，
  断言永远失败。**复刻真实时序**（让它超时，再点）才测到了东西。

## 2026-11-05 · 新窗口不会自己获得权限，而它失效的样子像时序问题

**场景**：输入窗打开后，点某一行的 ✎，目标行不刷新。我的第一反应是"`compose:open`
这个 emit 赶在窗口 `show()` 的那一帧丢了"——听起来很合理，因为窗口刚建、刚显示、
页面可能还没挂上监听。于是加了一条 500ms 的焦点轮询兜底，问题"消失了"。

后来为了写台账，顺手在 Tauri 的 ACL 上探了一下：

```js
invoke('plugin:event|listen', {…})  // 输入窗 → ERR: Command plugin:event|listen not allowed by ACL
invoke('plugin:event|listen', {…})  // 主窗   → OK: 4
```

**根本原因**：Tauri v2 的权限是白名单，`capabilities/default.json` 的 `windows` 只有
`["main", "bubble", "dashboard"]`。新加的第四扇窗**一条 core 权限都没有**，
所以它从来没收到过任何事件——不是"丢了一帧"，是**一次都没接上**。

**为什么这个 bug 能活下来**：因为三件事同时成立。
① 桥接层把 `listen` 的异常吞掉了（这是对的，`invoke` 会 reject 而渲染层没写 catch），
所以控制台干净。② 兜底轮询走的是**普通命令**（`compose_context`），不受 ACL 管，
于是功能照常工作。③ 我给它编了一个自洽的解释（"时序问题"），还写进了注释和台账。

**教训**：
- **"加了兜底就好了"是诊断的终点，不是修复的终点**。兜底救功能，救不了理解；
  一个"反正有兜底"的假设会让真正的失效活到下一轮。
- 新增窗口要动**两处**：命令白名单（`only(&window, …)`）和 capability 登记。
  前者管"能调什么"，后者管"有没有资格调"——**后者漏了，前者一条都不会被触发**。
- 兜底要配一条**能区分"兜底生效"和"主路失效"的断言**。现在回归里两条：
  `输入窗能 listen`（主路真的通）与 `输入窗 set_position 被拒`（没有多给权限）。

## 2026-11-05 · 验收脚本的 bug，会装成产品的 bug

**场景**：从桌宠发一句话，`say:done` 一直没来，60 秒超时。而应用日志里明明写着
`[say] 收工 ok=true id=Some("session-…") reply=收到`——后端从头到尾都是成功的。

**根因在脚本**：

```js
if (!done) done = await eval("JSON.stringify(window.__done||null)");
if (done && done !== "null" && fresh) break;
```

第一次轮询拿回的是**字符串** `"null"`（`JSON.stringify(null)` 的结果），它是 truthy，
于是 `if (!done)` 从此不再执行——后面五十多轮读的都是第一次那份"没有"。
事件第 9 秒就到了，脚本坚持说它没到。

**教训**：`JSON.stringify` 是个**把"没有"变成"有"**的编码器。拿它跨进程传值，
接收侧必须先解码再判空，而不是拿字符串跟 `"null"` 比——比的时候一个字母写错，
或者在它前面多加一个 `!`，就会得到一个"永远为假"的判据，而且它长得完全正常。
**判据一旦是"有没有东西"，就要在类型层面判**（`=== null` / `Object.keys().length`），
不要在序列化后的文本上判。

更值得记的是这次的**排查顺序**：我差点去查 `try_wait` 死锁、管道未关的写端、
`--json` 的 stdout 有没有被接住。这些都是"产品可能坏的地方"，而证据其实一开始就在
——手工在同一个目录跑同一条命令 7 秒就回话。**当同一个输入在 A 处通、B 处不通，
先怀疑 A 与 B 之间那层"测量"，再怀疑被测对象**。诊断日志（`eprintln!("[say] 收工 …")`）
是这轮唯一做对的事：它把"进程结没结束 / 有没有拿到 id / 有没有抓到答案"三件事
压进一行，一眼就能把范围从"整条链路"缩到"事件投递"。

## 2026-11-05 · 同一个问题问两次，会得到两个答案

**场景**：输入窗上写着「新会话 · Think」，发出去的消息却落在了 `…\project\DeepseekWorkSpace`。

**根因**：`compose_open` 和 `say_send` 各查了一次"最近有活干的会话在哪个目录"
（`latest_cwd()`），两次相隔几百毫秒，而这一轮里"最近有活干"换了人。
于是**窗口显示的和实际落地的不是一个值**。

**为什么这个 bug 比"显示错了"严重得多**：DSH 的会话是**按目录分桶**存的
（`~/.dsh/sessions/--E-JacksonLee-project-DeepseekWorkSpace--/`），
cwd 选错不是标签写错，是这条会话真的起在了另一个项目里——用户下次在那个项目里
看到一条自己没建过的会话，而且它还会被当成"最近工作目录"，下一句话继续错下去。

**修法**：`pinned_new_cwd()`，第一次算出来就钉在 `AppState` 上，两处都读它。
一般化的规则：**只要一个值会被"展示"和"执行"两个地方分别用到，就必须只算一次**。
两次算出来的东西即使逻辑完全一样，也会因为时间而分叉——而这里的时间差只有几百毫秒。

顺带把显示从 basename 改成**最后两段**（`…\project\DeepseekWorkSpace`）。
basename 在"确认这句话落到哪"这件事上是不够的：`…\project\a` 和 `…\work\a` 长得一模一样。

## 2026-11-05 · 只有 stdout 知道它回了什么

**场景**：看板上，从桌宠发出去的会话永远只有标题，没有"它答了什么"。

**根因**：`dsh headless` 建的会话，投影里**不写 `turnOutline`**——那一行是桌面端 /
网页端写的。投影里还有 `title` / `tokenUsage` / `contextPressure`，独独没有"这一轮
问了什么、答了什么"。同一类缺口还有 `modelSelection`（所以模型也是空的）。

**怎么补，以及怎么"不编"**：

- 问答：我们自己发消息时，`--json` 的 NDJSON 流里有 `final`。接住它，按 session id
  存成 `SayNote`，看板 join 上去，并且带一个 `reply_from_say` 说明**这段文字来自
  那一次发送**，不是从投影读的（投影会随会话更新，这一条只是"那一刻的答案"）。
- 模型：`dsh --profile headless --dump-config` 的 `agent-default-model` 是配置的
  权威展开（0.24 秒）。补上去，但必须带 `model_default` 标记，界面上写成
  「cmg · DeepSeek-V4.1-Flash-1017（默认）」。
- 轮数：`sessionStats` 缺失时退回 `turnBoundary.lastTurn`；其余字段**照旧不显示**。

**教训**：读别人的数据，"字段缺了"有两种原因——**没写**和**没到时候**。
前者要补来源，后者要等下一拍。把两者混成一句"读不到就不显示"，用户看到的是
一个永远空着的看板；把"补来的"和"本来就有的"混成一句，用户看到的是**一个善意的谎**。
这两件事都得在数据结构里分开（`reply_from_say` / `model_default`），不能只在界面上分。

## 2026-11-05 · 能不能续，是数据决定的，不是我们能绕的

**场景**：DSH 里有一类会话，`dsh headless --session-id` 直接拒不接：
`runs under agent preset "minimal", which the one-shot runner does not compose`。

**先确认它是什么**：`assertAdoptable()` 里的硬闸。桌面端 / 网页端建的会话带
`agentPreset`（一整套工具集配置），而一次性 runner 组不出那套 preset。绕过去的
办法显然存在（把 preset 字段抹掉），但那样做等于**用另一套工具集去写用户的会话**
——同一个会话在两边被两套系统提示、两套工具集轮流写，坏的是用户的记录。

**所以不绕，改成提前告知**：`can_resume` 在输入窗**打开的那一刻**就显示
「桌面端会话 · 只能看」。用户打了半屏字、按回车、然后才知道"这条不能续"，
那是设计问题不是提示问题。

**这条值得记的地方**：产品的"做不到"有三种——没能力、没权限、**对方不给**。
前两种可以靠工程解决，第三种只能靠界面说清楚。把第三种伪装成第一种（报个
看起来像 bug 的错）是最坏的选择：用户会一直重试。

## 2026-11-04 · "文件变了"不等于"用户说话了"

**场景**：用户报「没有任何任务，为什么一直保持 thinking？」。桌面上确实没有活干。

**根因是一条自我循环**，四步单看都合理，连起来是个锁死的圈：

1. `dsh headless` 的投影里没有 `sessionListMetadata`，`last_prompt_at` 只好退到**文件 mtime**；
2. mtime 每写一次盘就变（进程收尾时还会再变一次）；
3. 我把"这个值变了"当成"用户又提了一轮" → 发 `UserPromptSubmit` → 会话进 thinking；
4. 可这类会话不写 `sessionStats`，`phase` 永远判 Idle；而 Idle 分支有一道 `saw_active`
   闸（只有 working/thinking 分支才设置它）→ **永远不放行 Stop**。

结果：**一句话把会话关进 thinking，再没有谁能把它放出来。** 触发器是当天下午我自己跑的
两条测试命令（一条 401、一条 STREAM_CLOSED），死掉的会话安静地留在列表里，猫就一直想。

**三层教训**：

1. **`mtime` 只能回答"变过没有"，不能回答"谁做了什么"。** 用它当"事件"用，
   迟早把"文件被重写"读成"用户说了一句话"。凡是拿 mtime 兜底的地方，
   必须同时记下"这是兜底值"，并且**只让它参与"在不在窗口内"这种弱判断**。
2. **自己造出来的状态，自己必须收得回来。** 发 `UserPromptSubmit` 把别人推进 thinking 的那一段，
   没有同步置上"它是活跃过的"标记，于是回收逻辑永远不认账。
   **每一条"我让它开始"的路径，都要配一条"我能让它结束"。**
3. **thinking 是唯一一个"没有任何后续事件也能存在"的状态。** working 有工具事件兜着，
   attention 是 oneshot 会自己播完，只有 thinking 一旦没有后继就永远挂着。
   所以它必须有上限（`THINKING_MAX_MS` = 10 分钟）——这是**结构性**的兜底，
   不是给这次的 bug 打的补丁。

**为什么写了两层**：第一层修源头（不再发那个假事件），第二层修"再也不许有东西永远挂着"。
只修第一层的话，下一个事件源（第三方 hook、自己写的适配器）犯同样的错，猫还会再卡一次。
第二层是"无论谁把会话推进 thinking，它都会自己醒过来"。

## 2026-11-04 · 把字从猫身上挪下来：一个部件的删除，是另一处的设计题

**场景**：用户说「不要头巾了，也不要胸前的 RAG。任务状态直接以消息泡泡的方式弹出」。
头巾（`#rig-bandana`）是 S10 做的，戴在额头，上面写从 prompt 里抽的一个词。

**为什么该删**（不是用户挑剔，是那个位置本来就不够用）：布带中段能用的宽度只有 ~72px。
6 个汉字按 13px 排就是 78px，会顶出布带两边——所以字号要按字数分档缩到 10px，
而标题动辄十几个字，只能截前六个。用户看到「登录页重构登录」这种断句，
既不知道在干什么，也**答不了"什么状态""跑了多久"**——那才是他真正在问的事。

**关键判断**：删掉的东西，它承载的信息必须有去处。这里是从"物体上的字"
搬到"独立的层"：猫身上一律不印字（连那行金色 `RAG` 一起删——它解释不了任何事），
信息全部收进猫头顶的泡泡。**先想清楚信息去哪，再动手删**；反过来做，
就会在删完之后临时找个地方塞，最后得到一个比原来更差的位置。

三个坑，全是截图和断言逼出来的，代码复查看不出来：

| 现象 | 原因 | 解法 |
|---|---|---|
| 只有四条任务，泡泡里却出现滚动条 | 尖角写成 `#bubble::after`（`bottom:-7px`）。**绝对定位的后代会撑大"可滚动溢出区"** | 尖角改成兄弟节点 `#bubble-tail` |
| 尾巴指着空气，离猫头几十像素 | `bottom` 写死。单猫 176px 撑满、分身每只 88px 沉底，两者头顶差近百像素 | `placeBubble()` 按当前那只猫的耳尖实时算 |
| 位置偶尔偏高 | 量到了正在淡出的幽灵猫：退场的 `.cat` 还在 `#cast` 里留 1.6s，而 `#cast` 排在 `#layerA` 前面 | 按"当前真正在台上的 rig"取，不按 DOM 顺序 `querySelector` |
| 泡泡角啃掉头顶的 `✗` | 猫头顶还有一整套 FX 图标（attention 的 `!`、error 的 `✗`、zZz），比耳朵高 | 留 18px 而不是 8px。（**不能**用 `getBBox` 去量 FX：那些组用 `opacity` 控制，不可见的云朵也会被算进 bbox） |

**关于"进度"的一次拒绝**：用户要"查看具体进度"。agent 侧没有百分比，所以我只显示事实
（阶段 / 当前工具 / 已跑多久 / 目录），并在回复里直说"硬凑一个 0–100% 只能是编的"。
**编出来的进度第一天很懂事，第三天就开始骗人**——显示 90% 卡二十分钟，
用户会开始怀疑整个数据源，连那些真的数字也不信了。

**教训**：
1. **删部件之前先问"它承载的信息搬去哪"，而不是"删了会不会报错"。**
   报错是编译器的事，信息丢失是用户的事，后者从来没人在 CI 里发现。
2. **`overflow: auto` 的盒子里别放越界的绝对定位伪元素。** 它不算内容，
   但算"可滚动溢出"，于是你会为一个 7px 的三角形付出整条滚动条。
3. **"贴着"这种东西必须用断言钉，截图钉不住。** 只断言"泡泡在猫上方"，
   离着一百像素也是绿的；补一条"间距 0–40px"才真的钉住了"贴着"。
4. **写死的几何值，在两种形态之间必然错一边。** 单猫与分身、窗口缩放、
   DPI 变化——凡是"同一个 UI 有两种尺寸"的地方，位置都得实时算。

## 2026-11-04 · 读别人的数据目录：先问"这个文件还在被写吗"

**场景**：给桌宠接 DeepSeek Harness 的状态源。DSH 的投影缓存里有
`openStep`（在不在跑一个 step）、`firstTokenTime`（出首个 token 没有）、
`pendingCalls`（几个工具没落地）、`title`、`cwd`——正好是要的全部。
决定**只读投影缓存**，不碰 `session.v4.jsonl.zstd`（多帧 zstd，要引解压依赖）。

**现象**：代码写完、单元测试全绿、真实进程里 `reads` 在涨、`installed=true`、
4 条会话都解析出了标题——**但状态机里一条会话都没有**，猫一动不动。

**原因**：读错了文件。`~/.dsh/storages/` 下并排躺着两个东西：

```
session_projcache.json          ← 8 月 31 日，0.1.x 留下的单文件全量快照
session_projcache/              ← 11 月 4 日，0.2.x 用的目录，一会话一文件
    sessions/session-<id>.json
```

我读了前者。它格式合法、字段齐全、解析不报错，只是里面的会话全是**三个月前**的——
全部落在「30 分钟内才活跃」的窗口外，于是被过滤得干干净净。
**最坏的一种失败：不报错，只是什么都不发生。**

三个只有拆开文件才知道的事实：

| 事实 | 影响 |
|---|---|
| 新版是**每会话一个文件** | 反而更好：按 `(mtime, size)` 只重读变过的那个 |
| 形状是 `{version:7, record:{identity, rows}}` | 多了 `record` 一层，直接按老形状读会拿到 `undefined` |
| **会话 id 只在文件名里**，record 内没有 | 不能从内容取 id，必须用 `file_stem()` |

另外 `dsh headless "…"` 跑出来的会话**只有 `title`，没有 `sessionStats` / `sessionListMetadata`**
（连 `lastPromptAt` 都没有），所以那类会话得用**文件 mtime** 兜底判断"最近动过"，
否则它永远在窗口外、彻底看不见。

**解法**：改成扫目录 + 每文件 `(mtime,size)` 缓存；解析器只认 `record` 那一层，
拿不到就返回 `None`（不去猜别的版本）；`lastPromptAt` 缺失时回退到 mtime。
回归脚本改用**临时 `DSH_HOME` 夹具**，不再拿本机真实缓存做断言。

**教训**：
1. **读别的程序的数据目录，先确认"这个文件还在被写吗"。** `ls -la` 看 mtime 一秒的事，
   我是在"实现完 + 测试全绿 + 真机没反应"之后才看的。**并排两个同名物，几乎总是有一个是废弃的。**
2. **"读到了"不等于"读对了"。** 诊断计数 `reads` 在涨、`installed=true`、4 条会话带标题——
   每一个都在告诉我"成功了"。真正该问的是**这些数据是不是当下的**。
   所以诊断视图里加了一位 `has_stats`：解析成功但没有 statistics 行，是"格式对、内容旧/残缺"的指纹。
3. **拿真实环境做断言，等于让闸门看运气。** 第一版回归断言"会话要出现在 `/state` 里"，
   本机所有会话都超过 30 分钟没动静 → 必然 FAIL，而那**是正确行为**。
   后来改成现造现撤的夹具，顺带把「目录晚于进程启动才出现」这条路也验了。
   夹具撤掉后还要**等一拍**再往下走，否则多出来的那只猫会把后面
   「场上有几只猫」「attention 播完回 idle」三条断言全带偏——我第一次就带偏了三。

## 2026-11-04 · 整窗永久穿透：照抄了策略，没照抄底层能力

**现象**：用户跑起 exe 后「无法拖拽，也没有交互」。猫画得好好的，眼睛会跟着光标动（那是宿主推的），
但拖、点、双击、右键**全都没有反应**——像是点击被什么东西吃掉了。

**根因**：启动时 `set_ignore_cursor_events(true)`（四角不该挡桌面），原本的设计是
"页面收到 `mousemove`，命中 `#pet` 就调 `setIgnoreMouse(false)`"。这套写法是从 Electron 版搬过来的，
而它成立的前提在 Tauri 上**不存在**：

| | Electron 45 | Tauri 2（tao 0.37.2） |
|---|---|---|
| `setIgnoreMouseEvents(true, {forward:true})` | 设 `WS_EX_TRANSPARENT` **并**装一个低级鼠标钩子，把 `mousemove` 转发给窗口 | 只设标志，`forward` 参数在 Windows 上根本没有实现 |

tao 的实现只有一行（`platform_impl/windows/window_state.rs`）：

```rust
if self.contains(WindowFlags::IGNORE_CURSOR_EVENT) {
    style_ex |= WS_EX_TRANSPARENT | WS_EX_LAYERED;
}
```

`WS_EX_TRANSPARENT` 的语义是"我不参与命中测试"——鼠标消息直接交给下层窗口。
于是页面**一条 mousemove 都收不到**，"收到就关掉穿透"永远等不到触发条件，
整窗永久穿透。这不是"没生效"，是**自我死锁**。

**修法**：把判定搬到还在转的那一侧。渲染层每 200ms 上报一次"猫在哪"（矩形列表，CSS px，
分身时是每只 `.cat` 的包围盒，**不合并成一个大矩形**——合并会让两只猫之间的空隙变成挡板），
宿主每 60ms 读一次真实光标，落在矩形里就关掉穿透、离开就开回来。
拖动中强制不穿透：窗口追光标的 60ms 里，local 坐标有一拍可能落在矩形外，
一旦那一拍把窗口设成穿透，页面就收不到 `pointerup`，`drag_end` 永不到来，`dragging` 卡死。

**为什么四道闸门全绿还是漏了**：CDP 的 `Input.dispatchMouseEvent` 直接把事件注入渲染进程，
**绕过 OS 的命中测试**。所以合成事件照常触发 DOM 监听，`elementFromPoint` 也照常算得出猫，
75 条断言一条不少地通过——而真人用鼠标的时候，事件根本没进过窗口。

**教训（这一条比 bug 本身值钱）**：
1. **迁移时最危险的不是"没搬过来的功能"，是"搬过来了但依赖的底层能力没跟过来"**。
   功能清单可以对着抄，能力差异必须去读对方源码——这次读 `tao` 只花了三分钟。
2. **凡是"靠页面收到输入 → 再解除输入屏蔽"的设计，都要先问一句：被屏蔽的时候，输入还到得了页面吗？**
   答案是"到不了"的设计一律是死锁，只是要等一个真人来触发。
3. **合成事件的测试不能作为"输入链路通"的证据**，它只证明"处理逻辑对"。
   这两件事的差，正好等于"回归绿"和"用户点不动"的差。

## 2026-11-03 · 删容器之前，先把"谁还在用它的零件"画出来

用户说「现在有两个容器 Electron 与 Tauri，删掉 Electron」。九个文件，`git rm` 一行就完事——
真正花时间的是**在按删除键之前回答"删了之后谁会缺东西"**。三个发现，每种都能单独让构建红：

| 发现 | 如果不处理 |
|---|---|
| `src/server.js` 里躺着 `DEFAULT_PORT = 23333`，而 `hooks/install.js` 用它拼端点 URL | hook 装出来的 URL 变成 `undefined`，或者静默退回随机端口 |
| `src/theme.js` 被 `scripts/build-preview-bundle.js` 用（`listThemeIds` / `loadTheme`） | `npm run build:preview` 直接崩，预览页再也刷不出来 |
| `scripts/preview-shot.js` 整个是**基于 Electron 写的**（临时 app + CDP） | 七状态对照图从此没人能重新生成，而 README 里那张图会一直挂在那儿，看起来还挺好 |

处置分别是：`DEFAULT_PORT` 迁进 `src/port-file.js`（它本来就是"端点约定"的一部分，比 `server.js` 更该拥有这个数）；
`theme.js` 原位保留（它跟容器无关，只被 Node 脚本用）；`preview-shot.js` 移植到 Tauri——
起 release exe + `CLAWD_PORT_FILE` 隔离 + `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333`，
连上 CDP 后用 `Page.navigate` 把宿主窗口导到 `preview.html`。**WebView2 和 Electron 是同一套 CDP**，
所以移植的实质只有一句 `Page.navigate`。移植完实测七个状态全画出来了（目视确认）。

**教训**：`git rm` 是零成本的，找回功能不是。删除类任务的正确顺序是
"先列依赖 → 逐条迁出或确认共存 → 再删 → 跑闸门"，而不是"删完看什么报错"。
另有一条具体的：**别用目录名猜结构**。这次差点按 `ui/` 去找渲染层，
而这个项目的渲染层是平铺在 `src/` 下的（`index.html` / `renderer.js` / 三份 html + 两个 bridge）。

## 2026-11-03 · 签名三件事：cwd、被覆写的 exe、乱码日志

给发布物接签名，`signCommand` 配好、证书也生成了，仍然连撞三次。三次都长得像"签名没生效"，成因完全不同：

1. **`Cannot find module '...\src-tauri\scripts\sign-release.js'`**
   `signCommand` 的工作目录是 `src-tauri/`，不是仓库根。路径要写 `../scripts/sign-release.js`。
2. **日志说签了，产物却是 `NotSigned`**
   `cargo tauri build` 的日志里明明有 `[sign] signed: clawd-starter.exe`，但打包结束时
   `target\release\clawd-starter.exe` 的大小回到 4682752（签过的应该是 4690224，多出的是证书表），
   且 `Get-AuthenticodeSignature` 报 `NotSigned`——**打包器在签名之后又覆写了一次这个文件**。
   安装包不受影响（`makensis` 生成后才签）。所以 `npm run bundle` 里串了一刀补签。
   **教训**：验证"签没签"只能问产物（`Get-AuthenticodeSignature` / `signtool verify`），
   不能看日志。日志只能证明"命令跑过"。
3. **`[sign] 宸茬鍚嶏細nst45DE.tmp`**
   这个脚本的 stdout 会被 `makensis` 的管道接走，多字节代码页下中文被重编码。
   签名本身是对的，只是没法读。→ 脚本对外输出一律 ASCII，注释照旧中文。

还有一条差点误判的：`signtool` 报 `The file is being used by another process`——
上一轮回归留下的 `clawd-starter.exe` 还开着。这不是签名问题，先 `taskkill`。

## 2026-11-03 · 一条断言挪了 3px，永远够不着阈值

`gaze` 那条断言反复红。它本来就不稳定：gaze 线程有变化检测（偏差 < 0.02 不发），
光标静止时 0 次推送是**正确行为**，而断言写的是"这一轮至少推过一次"——
于是成败取决于测试期间有没有人碰鼠标。

上一轮的修法是"自己把光标挪一下再挪回"，挪 **3px**。今天读 `main.rs` 才发现为什么它照样红：

```
nx = (cx - 窗口中心) / 260        // 归一化

3 / 260 ≈ 0.0115  <  0.02        // 永远不触发
```

**要挪 ≥ 5.2px 才够得着**，改 8px（≈0.031）之后立刻稳定。
教训是两层：① 造"变化"之前先算清被测系统的判定单位，别拿感觉凑数字；
② 一条"看心情"的断言比没有断言更糟——它会训练你忽略红色。

## 2026-11-03 · 审计报告按 crate 名报，不看 target

`cargo audit` 第一次跑，425 个依赖、1402 条公告，结果 0 漏洞 / 2 条警告：
`proc-macro-error 1.0.4`（unmaintained）和 `glib 0.18.5`（unsound）。
差点顺手记成"两个已知风险，等上游"。

其实只要多打一条命令：

```
cargo tree --target x86_64-pc-windows-msvc -i glib@0.18.5
  → warning: nothing to print.
```

**它们根本不在 Windows 的构建图里**——来自 `tray-icon` 的 Linux 分支
（`libappindicator`/GTK），Windows 上托盘走 `Shell_NotifyIcon`，GTK 一行都不编译。
所以发出去的二进制不含这块代码，这不算"已知风险"，算"另一个平台的待办"。

`Cargo.lock` 是**所有 target 的并集**，而审计工具按 crate 名报，不带 target 信息。
所以读报告的最后一步永远是 `cargo tree --target <你要发的那个 target> -i <crate>`。
不做这一步的两种后果都很难看：虚惊一场（把不相关平台的公告当风险背一年），
或者把真问题当成"反正 Linux 才用"放过去。

两个工具坑顺手记下：① 让 `cargo-audit` 自己 fetch 公告库会报
`Failed to consume the pack sent by the remote`（libgit2），换 `git clone --depth 1`
五秒完成；② 旧版 `cargo-audit 0.21.2` 读不懂公告库里的 **CVSS 4.0**
（`unsupported CVSS version: 4.0`），要 0.22+——**工具比数据旧，报的错会指向数据**。

## 2026-11-03 · 一条会"看心情"红的断言：gaze 推过没有

复跑闸门时 `PASS 75 / FAIL 1`，红的偏偏是「gaze 至少推过一次」。
看着像回归，实际是**断言自己依赖了外部世界**：gaze 线程有变化检测
（光标位移小于 0.02 就不 emit，省 IPC 省电），所以光标静止时 0 条推送
是**正确行为**。那一轮机器没人碰，于是它红了。

这种断言的坏处不在假阳性本身，而在**它训练人反复重跑**。红一次、重跑就绿，
下次真红的时候所有人都会先重跑两次——那才是真正被它废掉的东西。

修法不是放宽判据（`>=1` 已经是最松的了），是**让测试自己造出条件**：
光标没动过就先挪 3px 再挪回去（PowerShell 调 `System.Windows.Forms.Cursor`，
Node 没有调 user32 的入口），等 400ms 再读。改完 `累计 5 次` 稳定 PASS。

注意这跟"用 PowerShell 的注册表 provider 绕过被安全策略拦掉的 `reg.exe`"
**不是一类事**：那是同一个动作换个壳硬做，这里是没有第二个壳可选
（要动的是操作系统光标，不是本进程状态）。

判据：一条断言如果需要"外部世界配合"，那它测的就不是代码，是运气。

## 2026-11-02 · 图标糊的真正原因：不是没画好，是"特征小于一个像素"

托盘图标（16~32px）看起来像一颗花椰菜。第一反应是"多打几个样本让它平滑"，
但抗锯齿只解决**锯齿**，不解决**分辨率不够**：256 设计单位里半径 15 的眼睛，
缩到 16px 只剩 0.94 个像素——画得再平滑，它也只能是"一层雾"或"没有"。

所以最终是两层修法，各管各的：

1. **超采样降采样**管边缘质量：4× 子样本判覆盖，RGB 只对覆盖样本求平均、
   alpha 取覆盖率。这里有个不显眼的坑：**不能把透明样本的颜色也平均进去**，
   透明像素 RGB 是 (0,0,0)，混进轮廓就是一圈脏灰边。等价写法是预乘 alpha
   再除回去，省一次乘法。
2. **简化几何**管特征存活：≤24px 换一套参数——眼睛放大、去鼻子去内耳、
   耳朵加厚外移。判断哪些特征必须活下来，标准不是"哪个重要"，
   是**"16px 的人凭什么认出这是猫"**：两个眼点 + 两个耳尖。就这三样。

顺带：检查小尺寸别靠肉眼盯原图——把 ICO 里的 16/20/24/32 抠出来、
最近邻放大 8 倍拼一张图再看。放大后的锯齿是真实信息（说明 AA 生效与否），
盯着 256px 的原图看永远发现不了 16px 的问题。

## 2026-11-02 · 两个"假证据"：一个来自观测太早，一个来自二进制太旧

追用户报的「thinking 掉成 idle」时，先抓到两个**看起来像真凶的假证据**。

**假证据一：诊断脚本自己读太早。** `diag-events.js --replay` 第一版输出
「SessionStart → null、UserPromptSubmit → idle ←– 掉了」。
按这个输出追了很久"UserPromptSubmit 为什么没映射"——EVENT_STATE 里明明有。
真相：回放第一步 POST 之后 150ms 就去 CDP 读渲染层，而页面还在加载，
`window.petDebug` 尚未挂上；等它挂上后读到的 `idle` 是初始化默认值。
**观测者把自己的时序写成了被观测系统的结论。** 修法：回放前轮询等
`typeof window.petDebug === 'object'`，等到才开跑。修完同一条链路 10 步全中期望。

**假证据二：debug 目录里的旧二进制。** 修完之后手滑跑了一次裸的
`node scripts/verify-tauri.js`（不带 `--release`），8 条 FAIL 齐刷刷：
`__TAURI__` 存在、白名单不拦、`/health` 缺 `lock` 字段——每一条都精确指向
一个"已经被修掉的东西又回来了"。实际是 `target/debug` 停在几小时前，
那批修复根本没编进去。这类失败最贵：现象完整、结论自洽，
唯一的破绽是**产物时间戳**。现在 verify-tauri 开跑前比对
源码 mtime 和 exe mtime，旧了直接退出并打印该跑的命令。

两条合起来的教训是同一个：**工具的输出不是真相，工具的输出加上"工具本身
处于什么状态"才是**。观测前确认观测窗口就绪，测试前确认被测物新鲜。

## 2026-11-02 · 开机自启：值必须带引号，勾必须写成功才动

Tauri 侧没有现成的 `app.setLoginItemSettings()`，自己写注册表：

- **落点用 HKCU 不用 HKLM**：`HKLM\...\Run` 要管理员权限，一个桌宠不配提权。
  HKCU 只对当前用户生效——桌宠本来就是 per-user 的东西，正合适。
- **值必须带引号**：`"C:\Program Files\clawd-starter\clawd-starter.exe"`。
  不带引号时路径一旦含空格，Windows 会把空格后面的部分当参数，
  开机表现是弹一个"找不到 XXX"的错误框，而且只在**别人**的机器上出现。
- **不引 `tauri-plugin-autostart`**：它连带拉 11 个包（auto-launch、objc2-*……），
  而我们只需要 `windows-sys` 的一个 feature（`Win32_System_Registry`）+
  五个 API（Open/Query/SetValue/Delete/Close）。四个函数五十行，值得自己写。
- **删一个不存在的值不算失败**：`RegDeleteValueW` 返回 `ERROR_FILE_NOT_FOUND(2)`
  时照样算成功——"关"要能重复按，幂等是这个开关的基本修养。
- **测试只默认验「关」**：开机自启是**进程外的全局状态**，写它等于改这台机器。
  测试中途崩了就留下一条真条目，下次登录自己弹一只猫。
  所以 `autostart_set(false)` 的幂等默认就测，「开」的往返要
  `CLAWD_AUTOSTART_TEST=1` 显式点名才跑。
- **勾的顺序**：先读当前状态 → 取反 → 写 → 写**成功**才 `set_checked`。
  反过来（先动勾再写）会在写入被系统拒绝时让菜单显示一个不存在的状态。
  Electron 侧同理：`setLoginItemSettings` 之后立刻读回
  `getLoginItemSettings().openAtLogin`，读回什么就显示什么。

## 2026-11-02 · 打包不是复制：`cargo build` 绿，说明不了"别人能装上"

第一次把这东西打成安装包。原以为就是 `bundle.active = true` 加几个字段，
真正花时间的全在**验收**上——而且验收的第一版判据是错的。

### 判据一："装出来的 exe 和裸 exe 的 sha256 相同"——错的

跑第一次就红了，只差 3 个字节。差值落在 `0x438a7f`，一看上下文：

```
装出来的:  ...__TAURI_BUNDLE_TYPE_VAR_NSS...
裸  exe :  ...__TAURI_BUNDLE_TYPE_VAR_UNK...
```

tauri-bundler 的 `patch_binary()` 会往二进制里打一个补丁，
把占位符换成安装包类型（`_NSS` = NSIS，`_MSI` = MSI），运行时
`tauri_utils::platform::bundle_type()` 读它。**打包从来不是复制。**

所以正确的判据是「除这段占位符之外逐字节相同」，而不是「哈希相同」。

### 判据二：这个占位符在文件里有 6 处

改成"跳过占位符"之后仍然红，报的是**"占位符被改成了 DEB"**。DEB 是 Debian 的包类型，
Windows 上不可能出现。原因是 `bundle_type()` 的 `match` 六个分支各是一份**字面量**：

```rust
"__TAURI_BUNDLE_TYPE_VAR_DEB" => Some(BundleType::Deb),
"__TAURI_BUNDLE_TYPE_VAR_RPM" => ...,
"__TAURI_BUNDLE_TYPE_VAR_APP" => ...,
"__TAURI_BUNDLE_TYPE_VAR_MSI" => ...,
"__TAURI_BUNDLE_TYPE_VAR_NSS" => ...,
_ => None,
```

`indexOf` 找到的第一个是 `_DEB`（第一行），真正被打补丁的是**最后一处**那个
`static mut __TAURI_BUNDLE_TYPE`。`lastIndexOf` 才对。

教训不是"要用 lastIndexOf"，而是：**判据写错时，失败信息会指向一个不存在的 bug**。
"占位符被改成了 DEB"这条如果不去核对，很容易变成"打包工具链有 bug"的结论。

### 判据三：卸载比安装难测

`uninstall.exe /S` 返回 0、exe 已经消失，但开始菜单那个 `.lnk` **还在**——
它比 exe 晚一步删。只看 exe 的后果不是当场红，而是**下一轮**的
"安装前不应有残留"基线断言红。一个错误的时间点，把失败推到了下一次运行。

改成一次等两个痕迹（exe + 快捷方式）都消失再断言，连跑两轮才稳。

### 工具被安全策略拦了：改判据，不改工具

本来想用注册表 `HKCU\...\Uninstall` 子键的增删来判"卸干净"。这台机器的安全策略
直接拦了 `reg.exe`。第一反应是"那我用 PowerShell 的注册表 provider"，但那是
**同一个动作换个壳**——拦的是这个动作，不是这个命令名。

换成两个真正的落盘痕迹：安装目录、开始菜单快捷方式。判据弱了一点（注册表条目不在覆盖范围内），
但**它是真的在测用户能看见的东西**。这条也写进了脚本注释，免得下一个人以为是偷懒。

### 打包带出来的两个"用户第一次装"才会遇到的问题

代码里完全看不见，但它们是真实体验的一部分，所以必须记在台账里而不是心里：

- **没有代码签名** → 双击是"Windows 已保护你的电脑 / 未知发布者"。要消除只能买证书
- **`webviewInstallMode` 默认 `downloadBootstrapper`** → 没有 WebView2 的机器会去微软下载，
  下载失败直接 `Abort`。**离线机器装不上**。要离线得换 `offlineInstaller`，
  安装包从 1.57MB 变成约 130MB

还有一个**不要去"修"的东西**：`cargo tauri build` 会吐两条

```
warning 6040: LangString "choowHowToInstall" is not set in language table of language English
```

`choow` 是 `choose` 的错拼，很容易当成"我们要补个语言字符串"。实际上这是 Tauri NSIS 模板
自己留的向后兼容兜底（模板里两处注释都写着 TODO：以后的大版本再删），
而且 `installMode: currentUser` 根本走不到那个页面。**看到一个 warning 先确认它是不是自己的。**

## 2026-11-02 · `WTSRegisterSessionNotification`：为什么不塞进 tao 的消息循环

"锁屏从轮询换成事件"听着是把 `OpenInputDesktop` 换成 `WTSRegisterSessionNotification`
就完事，真正要决策的只有一件事：**注册时交出去的那个 HWND 用谁的**。

### 三个选项，只有第三个能用

1. **塞进 tao 的窗口**。`WM_WTSSESSION_CHANGE` 是投给某个 HWND 的，要接住它就得改
   那个窗口的 wndproc。tao 没开放这个口子（Tauri 也没在外面再包一层），
   唯一能碰到的机会是 Tauri 自己的内部钩子——踩到别人实现细节上，升版本就碎。
2. **建一个普通窗口**。能注册，但它会进任务栏 / 参与 Z 序 / 出现在 Alt-Tab 里，
   为了接一条消息在用户桌面上多一个窗口，代价比晚 2 秒藏起来大得多。
3. **消息专用窗口**：`CreateWindowExW(..., HWND_MESSAGE, ...)`，父窗口给 `HWND_MESSAGE`。
   不显示、不进任务栏、不参与 Z 序，只收消息。**选这个。**

顺带一个好处：它跑在自己那条线程的 `GetMessageW` 循环里，和 tao 的消息循环完全不相交。
这个窗口出任何问题（注册失败、消息循环挂掉），画面那边一无所知——**故障不扩散**。

### `HWND_MESSAGE` 的代价：`RegisterClassW` 要 GDI feature

```rust
use windows_sys::Win32::UI::WindowsAndMessaging::{RegisterClassW, WNDCLASSW};
```

看着都在 `WindowsAndMessaging` 里，编译报 `E0432: unresolved import`。原因是
`WNDCLASSW` 结构体里有 `HICON` / `HBRUSH`，这两个类型归 `Win32_Graphics_Gdi` 管，
于是整个 `WNDCLASSW` 和配套的 `RegisterClassW` 都被 feature 门禁挡住了。

我们一个像素都不画，但**得在 `Cargo.toml` 里把 `Win32_Graphics_Gdi` 打开**，
否则连窗口类都注册不了。这类"要用 A 就得开 B 的 feature"的错误信息只说
`unresolved import`，不说为什么，得去翻 windows-sys 的 `features` 定义。

### `WndProc` 里不能等

第一版在回调里直接 `w.hide()`。`hide` / `show` 是 Tauri 的 API，它要把请求投递到
主线程并**等一个回执**——在 `WndProc` 里等，就是把这条消息线程卡住，
后面的锁/解锁消息全排队。所以回调只做一件事：把 `bool` 丢出去，`spawn` 一个线程再动窗口。

```rust
let wired = sys::watch_session(move |locked| {
    let app = watcher_app.clone();
    std::thread::spawn(move || apply_lock(&app, locked));   // 不在 WndProc 里等
});
```

这里同时踩了个借用错误：`let app = app.clone()` 之后外层 `if !wired` 里还要用 `app`，
`E0382: borrow of moved value`。改名 `watcher_app` 解决——**名字取成两个不同的，
比在脑子里记"这个 app 已经被移走了"可靠。**

### 只认两个 `wParam`

`WM_WTSSESSION_CHANGE` 的 `wParam` 有 8 种取值。第一反应是"不是 `UNLOCK` 就算锁屏"，
这个写法会把三条完全不该藏的场景算进去：

- `WTS_REMOTE_DISCONNECT` (3)：远程桌面断开，**人还在电脑前**，只是换了块屏幕
- `WTS_CONSOLE_DISCONNECT` (4)：同上
- `WTS_LOGOFF` (5)：注销，进程本来就该退

所以是白名单，不是黑名单：只有 `LOCK` (7) 藏、`UNLOCK` (8) 显，其余 `return 0` 不动。

### 把"当前是什么模式"暴露出来

"锁屏后没藏窗口"这种问题**没法当场复现**——你得先锁屏，而锁屏之后你看不见窗口。
更麻烦的是：事件注册失败时会自动退回 2s 轮询，**两种模式下"没藏"的样子一模一样**。

所以 `/health` 多了一个字段：

```json
{ "ok": true, "lock": "event" }
```

回归里钉一条 `lock === "event"`。这条断言的价值不在"验证功能正常"，
而在于**下次有人报"锁屏没生效"时，第一句话能问出"是 event 还是 poll"**。

### 最后：哪一段没被验证

单测覆盖"投 `WM_WTSSESSION_CHANGE` → 回调收到 true/false"，
回归覆盖"注册成功（`lock: event`）"。**中间那段没覆盖**：事件 → `apply_lock()` →
窗口 `hide()`/`show()`。真锁屏没法进回归（会把跑测试的人踢出桌面）。

所以这条必须写在台账里，否则 **74 条全绿会被读成"锁屏行为整个被覆盖了"**。
剩下那十行靠人工锁一次屏验——今天验过了。

## 2026-11-02 · 关掉 `withGlobalTauri` 之后，通用口子**还在**

任务清单上写的是"关掉 `withGlobalTauri`，让 `core.invoke` 不再挂在 `window` 上"。
做完之后才发现这句话只对了一半，而错的那一半比做对的那一半重要。

### 先说对的部分

`tauri.conf.json` 改一行 `false`，`window.__TAURI__` 就整套消失了——
`core.invoke`、`event.listen`、`path`、`window` 全都没了，回归一条断言钉着。
桥接改成自己拼 8 行（`invoke` + `plugin:event|listen`），
事件推送一切正常（68 条断言全绿，说明 listen 那三个参数拼对了）。

`listen` 这三个参数值得单独记一笔，因为**最容易错的是最后一个**：

```js
invoke("plugin:event|listen", {
  event: name,
  target: { kind: "Any" },
  handler: I.transformCallback(cb),   // ← 不是 cb，是 transformCallback(cb)
});
```

凭直觉会把 `cb` 直接传进去，然后得到一个"注册成功、但回调永远不触发"的静默失败。
参数形状是去翻 `tauri-2.12.5/src/event/plugin.rs` 抄的
（`listen(webview, event: EventName, target: EventTarget, handler: CallbackFn)`），
`EventTarget` 是 `#[serde(tag = "kind")]`，所以是 `{ kind: "Any" }` 而不是字符串。

### 再说错的那一半

我以为 `__TAURI__` 是 Tauri 在 `__TAURI_INTERNALS__` 外面包的一层便利 API，
那关掉它，底下的东西应该也不远。写了个探针一测：

```
typeof __TAURI__            : "undefined"
typeof __TAURI_INTERNALS__  : "object"
internals 自有键            : ["plugins"]
internals 描述符            : {"value":{...},"writable":false,"enumerable":false,"configurable":false}
可删除吗                    : false
通用 invoke 还在吗          : "function"
```

`writable: false` + `configurable: false` = **既不能覆盖也不能删除**，
而且它不在 `Object.keys(window)` 里（`enumerable: false`），所以肉眼扫一遍 `window`
是看不见它的。Tauri 把它做成不可配置是有道理的：那是整个 IPC 的地基。

所以结论必须写清楚，不能含混过去：

> **关掉 `withGlobalTauri` 缩小的是"可发现面"，不是"通用调用口"。**
> 想靠这一步把 Electron 那条边界（`contextIsolation` 下连 `ipcRenderer` 都摸不到）
> 找回来，是找不回来的。

最初我打算"取完引用就 `delete window.__TAURI_INTERNALS__`"，探针直接把这个方案否了。
如果没有先测、直接按计划写，会得到一个看起来很严密、实际什么都没做的桥。

### 于是边界换到 Rust 侧

JS 那边关不干净，就只能在后端判。16 条命令全部加 `window: WebviewWindow`
（Tauri 会注入调用方那个 webview），进门第一句 `only(&window, W_MAIN)?;`。

写的时候发现一个小陷阱：`pet_menu` 原来是 `app.get_webview_window("main")` 拿到窗口再
`popup_menu`。加了注入参数之后，如果继续用 `get_webview_window`，那"菜单弹在谁身上"
就取决于"两处查询是否一致"——多了一个不必有的假设。改成直接用调用方那扇窗，
白名单已经保证它是 main 了。

回归里三条越权断言都**绕过 `window.clawd`、直连 `__TAURI_INTERNALS__.invoke`**。
这是有意的：走桥测的是"桥有没有拦"，而桥是我们自己写的、随时能被下一个人改；
直连测的是"Rust 拦不拦得住"，那才是边界。

### 一条不许忘的边界说明

白名单按**窗口**分，不按**调用来源**分。主窗口真被注入了脚本，它照样能调主窗口那 8 条
（含 `app_quit`）。这不是新引入的问题——Electron 版注入了脚本同样能调 preload 那 12 个动作。
但**别把"加了白名单"当成"渲染层被关起来了"**：它解决的是越窗口，不是同窗口内的越权。

## 2026-11-02 · 单实例锁：**判据说反了，代码就会写反**

补的是 S10-5 漏掉的 `requestSingleInstanceLock()` 等价物。但真正值得记的不是
"命名互斥量怎么写"，是**台账里那句描述本身是错的**：

> 「开第二份 → 回退随机端口 → 影响是桌面上出现两只猫、hook 仍然打给第一只（端口没变）」

写的时候觉得"端口是固定的 23333，第二份抢不到就随机，那原来那份没变啊"。
**错在把"第一份没变"当成了"端点文件没变"。** `server::start()` 里
`write_port_file()` 是无条件执行的（`server.rs:234`），第二份拿着它的随机端口
把文件**覆盖**了。所以真实后果是：

- hook 读端点文件 → 拿到的是第二份的端口和 token → 事件全送进第二份
- 用户屏幕上那只猫是第一份的 → 它一个事件都收不到 → **画面永远不动，且没有任何报错**

"安静的坏"比"报错的坏"难查一个数量级。这条描述在台账里躺了一整天，
S10-6 动手时逐行核对才发现的——**台账里凡是"影响是……"的句子，都要回到代码里指一行**。

### 为什么是互斥量而不是锁文件

第一反应是写一个 `.lock` 文件。问题是它没有可靠的释放路径：

- 进程被任务管理器强杀 / 崩溃 / 断电 → 文件留下 → 下次启动误判"已经在跑"
- 于是要存 pid，启动时查这个 pid 还活着没 → **pid 会被复用**，查到别的进程头上
- 于是要加时间戳 + 超时 → 超时内重启又被误拦

三层补丁每层都能出错，而它们要解决的问题（"谁在持有"）内核本来就管着。
命名互斥量的句柄随进程消失被内核释放，所以 `ERROR_ALREADY_EXISTS` 永远是真的，
**零清理逻辑**。这类"操作系统已经替你做了"的判断，值得多花十分钟去找。

### 自己写的测试把功能拦住了

加完锁立刻跑回归，第一反应是"应该全绿"。实际是**整套 68 条会全部挂掉**——
因为回归脚本本来就是"再起一个进程"，而它靠 `CLAWD_PORT_FILE` 指临时文件，
就是为了能在用户正开着桌宠的时候跑。锁名要是固定的，回归一启动就被自己拦住，
表现是"进程秒退、主窗口 20s 内没暴露 CDP"。

修法不是"跑回归前先关掉锁"，而是把**锁的身份定义对**：锁要保护的是
"一个端点文件 + 它里面那个固定端口"，不是"这台机器上只能有一个 clawd"。
所以名字带上端点文件路径的哈希。同一个端点文件 = 同一个实例，不同端点文件各管各的。
生产环境下没有 `CLAWD_PORT_FILE`，两边落到同一个 userData 路径，行为不变。

哈希用 FNV-1a 手写了 6 行，没用 `DefaultHasher`：后者的输出**没有跨版本保证**，
升一次 Rust 就可能换一个锁名，那会变成"多开限制偶尔失效"这种极难复现的 bug。

### 判据要选"接近需求"的那个

"第二份进程退出了吗"是最容易写的断言，但它只证明了一半。真正的需求是
**"第二份不许碰第一份的通信链路"**，最接近的判据是**端点文件一个字节都没变**。
所以回归里三条断言是：进程 5s 内以 0 退出 / 端点文件字节未变 / 用原 token 打
`/health` 还是 200（顺带证明 token 没被换掉）。

## 2026-11-02 · 容器换成 Rust（Tauri）：**三个 bug 是跑起来之后才浮出来的**

用户的原话是「我装了 Rust。装工具链后迁 Tauri」。三条需求里的第二条
（"把后端与窗口容器用 Rust 重写，常驻内存 15MB 以内"）到这一步才算有人动手。

结论先写：**后端确实做到了，整机没有**。Rust 宿主进程私有内存 **11.2MB**（达标），
但窗口里跑的还是 Chromium（WebView2），整机常驻 **约 383MB**，和 Electron 的 **370MB** 基本持平。
"15MB"这个数在任何 WebView 方案下都拿不到，只有原生自绘才行——而用户明确否掉了自绘
（"我要线下手动画吗？"）。**这不是执行不到位，是目标本身和所选方案互斥**，
应该当面说清楚，而不是把 383MB 描述成"接近 15MB"。

### 迁移顺序：先把判据钉死，再动代码

`src/risk.js` 的 16 条用例先在 Rust 里重写一遍 `#[cfg(test)]`，断言两版判据一致；
`state.js` / `theme.js` 各自有 6 条、`permission.js` 4 条。**先有等价性证明，再删 JS 版**——
反过来的话，重写过程中"悄悄把判据挪动一格"这种错误，只有在真实 agent 跑歪了之后才会暴露，
而那时候已经没人记得原判据是什么了。

### 三个 bug，全部是"接口通、画面不动"

这三个的共同点：**没有任何一处报错**。HTTP 200、invoke 返回 ok、控制台干净。
它们是跑起来对着屏幕看才发现的——这也是为什么这次坚持要有 `verify-tauri.js`。

#### ① `POST /state` 的 `changed` 被 `let _ = changed;` 丢掉了

`Store::apply()` 内部已经调过 `tick()`，而 `tick()` 会**顺手把 `last_visual` 更新成新值**。
等 250ms 心跳再跑一次 `tick()`，它比的是"新值 vs 新值"，返回 `false`——
这次变化就**永远不会被推出去**。

症状极具迷惑性：`/state` 回包里 `visual` 是对的、`cast`（1s 定时推）里会话状态也对，
**只有画面停在旧状态**，直到下一次状态变化才追上来。

Electron 版没这个问题，因为 `state.js` 的 `apply()` 末尾直接 `emit()` → `onChange` 回调。
Rust 版把"算 change"和"推 change"拆到了两个文件里（`state.rs` 算、`server.rs` 看了却没推），
拆的时候没人负责那根线。

修法：`server::start` 收一个 `OnChange = Arc<dyn Fn(&Snapshot)>` 回调，
`main.rs` 把它翻译成 `emit("state", snap)`。
**不用 `AppHandle` 直接塞进 server**：那一层刻意不认识 tauri，
塞进去之后 `server.rs` 的每条单测都得先起一个 Tauri 应用。

#### ② 第一条权限请求永远不会弹窗：窗口没建出来

`show_bubble()` 里，`bubble_ready == false` 时把请求塞进 `bubble_pending` 就返回了——
**但没人建窗**。而 `bubble_ready` 这条握手信号是**页面发出来的**，页面要加载就得先有窗。

死循环：没窗 → 没页面 → 没 ready → 请求一直躺在槽里 → HTTP 那头挂到超时 → 回落 204。
用户从头到尾**什么都没看见**。整条权限气泡功能在"第一次使用"这个场景下是死的
（第二次能用，因为第一次超时后窗被建过？不，是根本没建——所以是每次都死）。

Electron 版把"建窗"和"等 did-finish-load 再投"绑在同一个 `createBubbleWindow()` 里，
拆成 `show_bubble` / `present_bubble` 两个函数之后就漏了。

#### ③ 在命令线程里建窗 → 死锁；`app.exit()` 顺便一起陪葬

`dashboard_toggle` 里直接 `WebviewWindowBuilder::build()`。窗口**建出来了**
（`/json/list` 里能看到一个 `about:blank`），但**永远不导航**，
而且这条 invoke 永远不 resolve（5s 后 CDP 那侧超时）。

更坑的是它把 `quit()` 也带坏了：`app.exit(0)` 只是往消息循环投一条消息，
而消息循环正卡在我们这一帧里——没人去泵它。于是"点退出没反应"。

同一段代码从 **HTTP 线程**调就没事（`show_bubble` → `ensure_bubble` 建气泡窗口是好的），
因为那时消息循环是空闲的。**所以判据不是"能不能建窗"，是"从哪个线程建"**。

修法：`dashboard_toggle` / `app_quit` 都挪进 `std::thread::spawn`。
改完之后 `quit` 从"8 秒不退"变成 **201ms 退出**，端点文件也删干净了。

### 桥接层：让容器换掉而渲染层一行不改

`src/tauri-bridge.js` 在 `window` 上装出和 `preload.js` 形状相同的
`clawd` / `bubble` / `dashboard` 三个对象。`renderer.js` 里那些 `if (window.clawd)`
的判断本来就是为"浏览器预览模式"留的，现在正好复用：**切换宿主在渲染层看来是透明的**。
Electron 下这个文件第一行就 `return`（没有 `__TAURI__`），所以三份 HTML 两边共用。

有两处不能照抄：

- **`listen` 是异步的，`ipcRenderer.on` 是同步的。** 三个渲染层都是"先 on、后 ready"的顺序假设。
  气泡那条最要紧：`onRequest(render)` 之后立刻 `ready()`，而主进程收到 ready 就会把攒着的
  第一个请求吐出来。所以每条通道在**脚本加载时**就挂上，`ready()` 再显式等一次那条 Promise。
- **`send` 一定要吞异常。** `ipcRenderer.send` 从不 reject，渲染层因此一行 catch 都没写；
  Tauri 的 `invoke` 会 reject（命令不存在、参数不符、命令里 `return Err`）。不吞就是刷屏的
  unhandled rejection。

### 动了 CSP（硬约束 20），理由和代价都写进 meta 注释了

`connect-src` 从 `'none'` 放宽到 `ipc: http://ipc.localhost`。
这不是"顺手开个口子"：Tauri v2 的 IPC 不是进程内通道，是
`fetch("ipc://localhost/<cmd>")`，Windows 上落成 `http://ipc.localhost`，
**属于标准网络请求，会被 `connect-src` 拦**。`tauri-utils/src/config.rs` 的 CSP 注释里
给的就是这两个值。

只放行这一个假域名，公网依然一个都连不上。写在这里是因为：**下一次有人想再放宽 CSP 时，
得先看到这次的理由，而不是看到"上次也放宽过"就当成惯例**。

### 回归：两份，判据同源

- `scripts/verify-electron.js` 仍然是 **191 PASS / 0 FAIL**（这次只改了一处：把 CDP 客户端抽成
  `scripts/cdp.js` 共用）。
- 新增 `scripts/verify-tauri.js`，**65 PASS / 0 FAIL**。

为什么不复用同一份脚本：Electron 那 191 条里有 12 条打的是**主进程 Node inspector**
（`BrowserWindow.getAllWindows().length` / `ipcMain.listenerCount()`）。
Tauri 的主进程是 Rust，这些断言既没有入口也没有意义。硬套只会得到一堆"跳过"，
而**跳过是不算数的绿**。

三条断言在写的过程中被改掉，值得记一下，因为它们暴露的是"我以为的行为"和"实际的行为"不一致：

- `Stop` → **attention**（不是 idle），2400ms oneshot 后才回 idle。原来那条断言写错了。
- 猫是**故意重叠**的（用户原话"有重叠"）。断言"不重叠"是在拿自己的臆想当规格。
- gaze 线程有变化检测（偏差 < 0.02 不发）。断言"1.2 秒内至少 5 条"必挂。
  该断言的是"至少成功推过一次"——它同时证明 `GetCursorPos`、线程、emit、桥四段全通。

### 顺带学到的一件事

`about:blank` 的 CDP 目标**不代表窗口没建**，它代表"窗口建了、页面还没导航"。
早期我按"有 target 就算建窗成功"判断，把 ② 和 ③ 混成了一件事。
分开它们靠的是直接读那个 target 的 `location.href` 和 `typeof window.__TAURI__`。

### 入库前：4.0 GB 的 `target/` 差点跟着进去

跑台账巡检脚本时它报了 7000 多个没登记的文件，全是 `src-tauri/target/**` 下的 `.d` / `.pdb` /
`.dll.exp`。查了一下：**4.0 GB，7588 个文件**——`git add src-tauri` 会把这些当成新文件一起暂存。
当时 `.gitignore` 里没有它（这个仓库此前没有 Rust 代码），巡检脚本的 `SKIP_DIRS` 也没有 `target`。

两处都补了：`.gitignore` 加 `src-tauri/target/` 和 `src-tauri/gen/`（后者是 Tauri 每次构建
重写的 ACL schema 快照）。补完再 `git add -A src-tauri`，暂存列表是 15 个文件，正好是源码 +
配置 + 三个图标 + `Cargo.lock`。

**教训**：换一套工具链之后，`.gitignore` 和"哪些目录不算源码"这两个老约定会静默失效——
它们不报错，只是让 `git add` 变得很危险。巡检脚本恰好是能发现这件事的东西，前提是有人跑它。

## 2026-10-30 · 信箱整套删掉：它解决的是一个不存在的问题

上午刚给信箱加了「报告问题…」入口，下午整套砍了。触发是用户一句判断：

写 → 存进磁盘 → 等下一次 `UserPromptSubmit`，而且中间那个"存"的环节
正是前一天吃掉一封信的地方（fire-and-forget，没有回执，`take()` 一挪走就消失了）。
一个"更容易丢、还更慢"的替代品，不值得为它保留一整个子系统、四个文件、49 条断言。

### 删完之后连带的三件事（比删代码本身费事）

1. **手势不能空着**。双击原本是"写信"，砍掉后如果直接删掉 handler，
   用户双击桌宠会毫无反应——而桌宠没有标题栏，双击是他唯一能自己试出来的动作。
   所以双击改回"开关看板"，和右键菜单里那一项同一个 toggle。
2. **`store` 从模块级 `let` 退回 `whenReady` 里的 `const`**。
   它当初被提出来，是为了让诊断包读 `store.snapshot()`。消费者没了就退回原样——
   **改动要按它的起因回滚，不是按"看起来更简洁"回滚**。
3. **文档与台账全套跟着删**（硬约束 1）：`README` 的 S8 整节、`FILE_MAP` 的四行文件条目
   和整条"送信流"、`SECURITY` 的 SEC-12 / SEC-15、`PROJECT` 的阶段表与三条硬约束、
   `GLOSSARY` 的速查卡、`verify` 的 49 条断言。
   **判据只有一个：这个字段/这个功能还有消费者吗。**

### 反面教材：我删错了一个常量，而它是"看起来属于这个功能"的

删送信段时我把 `IGNORED_NOTIFICATION_TYPES` 一起删了——它就在那段附近，
看着就是送信的一部分。实际上它的消费者在**收**的方向上（过滤 Notification 噪音）。

后果：`ReferenceError` 被 hook 末尾的 `main().catch(() => {})` 静默吞掉，
**所有 Notification 都发不出去、零报错**。唯一发现它的是回归里那条
「对照组：真的通知照常放行」——**一条对照组断言救了整条链路**。

教训：删代码时按**使用点**框范围（`grep` 每个名字），不要按"它写在哪一段"框范围。
以及：**`catch(() => {})` 是有代价的**，它把"我把常量删没了"变成"这个功能今天不工作"。

## 2026-10-30 · 用户拿"写信"当 bug 反馈渠道，说明我们缺一个入口——但别顺手造第二个投递口

> **后续（同一天下午）**：下面这条里做的「报告问题…」入口**随信箱整套删掉了**。
> 里面两条通用结论留了下来——① 给新内容定隐私口径要按全部归宿里最严的那处定；
> ② 原生菜单在回归里测不到，要给它留一个可编程入口。

用户的第一份 bug 报告是**写信**说的：「需要我确认的时候，没有提示我啊」。
他走的是"跟猫说话"那条路，因为桌宠身上当时没有一个更像"反馈"的地方。

于是补了一个入口：**右键菜单「报告问题…」**。它和「写封信…」只差两件事——
预填现场诊断、寄出时本地留一份副本。

**这条改动里最要紧的不是"加了什么"，是"没加什么"：它没有开第二个投递口。**

前一天我们刚因为多开一个投递口（`SessionStart`）吃掉一封信，所以这次每一步都得先问
「这条路失败了，我看得见吗？」。逐条对照：

| 想加的东西 | 会不会吞东西 | 结论 |
|---|---|---|
| 第二个投递口 | 会——`take()` 一挪走就消失，宿主又不回执 | **不做** |
| `reported/` 本地副本 | 不会——它**不参与 `take()`**，永远不会被挪走 | 做 |

副本唯一的身份是**回执**：hook 是 fire-and-forget，"有没有送到"我们确认不了，
但"我提交过了"必须查得到——用户真的问过「我写的信，没了?」。

**教训**：被一个缺口提醒之后，最容易犯的错是沿着上次出事的那条路再走一遍。
缺口的形状是"没有入口"，不是"没有第二条船"。

## 2026-10-30 · 落盘内容有两个归宿时，隐私口径按更严的那个定

诊断文本写完之后我去想"它最后会去哪儿"，答案是**两个地方**：
① 跟着信进 agent 的上下文；② 作为副本留在用户磁盘上。

所以判定字段能不能进诊断的标准不是"进上下文合不合适"，而是
**"两处里更严的那一处能不能接受"**。项目目录名在两处都 unacceptable：
它可能含客户名、内部代号。最终诊断里只有状态与事件序列，**cwd 一个字都不取**。

顺带把长度也钉死了（1200 字上限）：它会挤占用户下一条消息的上下文预算。

**教训**：给新内容定隐私口径时，先列**全部归宿**，再按最严的那处定标准。
只看一处等于默许它在另一处泄漏——而且那处往往没人盯着。
这次还特意做了敏感性抽查：临时把 `cwd` 注入诊断，那条隐私断言确实变红了
（恢复后回绿）。**一条从没红过的隐私断言等于没有。**

## 2026-10-30 · 「没有提示我」：把持续状态当成一次性闪光，是最安静的那种功能缺失

用户写在信里的原话：「需要我确认的时候，没有提示我啊」。

信在 `sent/` 里躺了一天我才发现——**值得单独记一笔的是：用户报的 bug 走了一条我们没设计过的投递路线**（双击桌宠 → 写信 → 随下一次 UserPromptSubmit 送出）。那条路本来是给"我想让 agent 知道点什么"用的，用户拿它当 bug 反馈渠道，说明**桌宠身上没有一个更直接的反馈入口**。这是另一个缺口，先记着。

回到这句抱怨本身。它的根因只有一处，但藏得很深：

```
ONESHOT = { error: 2600, notification: 3200, attention: 2400 }   // 内置
theme.json.timings.oneshot.notification = 1500                   // ragdoll 主题又改短了一半
```

`notification` 和另外两个被塞在同一个语义里——"播一次就走"。但它在表达的东西根本不一样：

- `error` / `attention` 是一个**瞬间的事实**（"刚才失败了"、"这一轮说完了"），播完该消失，留着是噪音。
- `notification` 是一个**持续的状态**：agent 正卡在那儿等你点"允许"。主仓库管它叫 `a real permission hold`（`clawd-on-desk/src/state.js:345`）。

1.5 秒的闪光意味着：提示出现的那一刻，用户的眼睛大概率不在桌宠上（他在看终端、看编辑器、或者根本在想别的事）。等他抬头，屏幕上什么都没有。**功能"正常"，用户"没收到"——这两件事同时成立，而且日志里没有任何异常。**

改法是把语义分开：`notification: 10 分钟`（对齐主仓库 Kimi 权限 hold 的兜底上限，那里的注释写着"真实用户常常在 TUI 前耗上几十秒——接电话、吃饭、犹豫"），并且明确写下**真正让它消失的不是这个计时器，而是下一个事件把它顶掉**；10 分钟只是"从此再没有任何事件"时的兜底，否则提示会永远挂在屏幕上。

**教训**：一个字段的语义要按"它在表达什么"分组，不能按"它们都用同一个机制实现"分组。`error`/`attention`/`notification` 共用一套 oneshot 定时器，于是三个被写进同一张表、读成同一种东西——而其中一个的时长单位其实是"等待"，另外两个是"播报"。**共用机制不等于共用语义。**

## 2026-10-30 · 修长状态之前，先把"霸屏"的前提问一遍

把 `notification` 从 1500ms 改成 10 分钟，立刻暴露出一个一直在、但没人看得见的 bug：

```js
if (oneshot && now < oneshot.until) visual = oneshot.state;   // 原来
```

只判时间，不问"还有没有人真的处在这个状态"。于是：

> 权限提示挂上来（上限 10 分钟）→ 用户点允许 → agent 继续干活（`PreToolUse` → working）
> → **画面上猫还在喊**，因为那个 `until` 还没到。

同一个 bug，在 800ms 的 `attention` 上只是"偶尔闪错一下，没人看得出来"，在 10 分钟上就是"明明在干活、猫喊了整整十分钟"。**是这次改动让它第一次变得要紧，但它一直都在**——这类 bug 的可见度和它所依附的时长成正比，所以短时长是一种伪装。

修法是给霸屏加一个前提：`sessionsHave(oneshot.state)`——必须还有会话真的处在这个状态。语义也就干净了：**霸屏的意思是"真的还有人在喊"，不是"上一次喊的时刻还没过期"。**

顺带一条assertion写法上的教训：我最初的断言里手抄了一份 `{oneshot:{notification:1500}}` 当输入，理由是"要证明用户遇到的就是这个数"。主题改好之后它反而红了——因为抄的那份已经不是真实值了。改成**直接读 `themes/ragdoll/theme.json`** 才对：手抄的常量只记录这一次的历史，主题哪天又被写回 1500 它照样绿，那不是盯着它的断言，只是一张旧照片。

## 2026-10-30 · 每多一个投递口，就多一个能把信带走却不一定送到的地方

前一天给送信加了第二个投递口 `SessionStart`（理由很正当：官方点名的两个例外里就有它，WorkBuddy 每轮都补发，不必等用户真的开口）。**启用一天就吃掉了一封信。**

用户的原话：「我写的信，没了?」

查证：`pending/` 是空的，`sent/` 里躺着两封。第一封（10-28「不想要布偶猫前面的围兜了」）送达了——第二天的改动就是证明。第二封（10-29「需要我确认的时候，没有提示我啊」）被 `take()` 从 pending 挪到了 sent，**但没有进上下文**。

这正是 `mailbox.js` 里 `take()` 那条注释发誓要防的黑洞："先挪后算，宁可下一轮重寄，也不留'取走了没寄出去'"。**结果我们自己在另一个文件里造了一个。**

根子在于 hook 是 **fire-and-forget**：写完 stdout 就 `exit(0)`，宿主从不回执。所以"投递成功"这件事我们**根本没有确认手段**——`take()` 一 rename，信就从 pending 消失了，而它是否真的进了对面的上下文，永远没人知道。于是判据只剩一条：**只守实测最可靠的那一个口**。

已经回滚成只有 `UserPromptSubmit`。那段注释我没有删，就留在 `clawd-hook.js` 的 `CONTEXT_EVENTS` 上方，让下一个想"顺便再加一个口"的人先看见代价。

**教训**：一个"理论上也行"的通道，在没有回执的协议里不是"多一条路"，是"多一个可能吞掉东西的黑洞"。**先问：这条路失败了，我看得见吗？** 看不见的话，它带来的不是冗余，是风险。

## 2026-10-29 · 「别的产品能，我们为什么不能」——答案往往在别人房间的那一侧

用户的原话：「微信可以直接发消息给 workbuddy，正常来说这条路是通的啊？和 ragdoll 说完，还要通过下次和 workbuddy 的信息一起发出去，这样很蠢啊」。

这句话有两个部分：**上半句是技术判断，下半句是体验判断**。它们得分别处理，而且都不能靠「我猜是这样」回应。

- **先验证上半句，别急着反驳也别急着认输。** 本机真的存在一条 IPC：`%USERPROFILE%\.workbuddy\wbipc\endpoint.json` 里是一个命名管道加一个 ticket。写了个**只读探针**（只握手、只 `broker/ListPipes` / `broker/GetPipe`，绝不碰写方法），握手一次通过——**用户的直觉是对的，路确实存在**。
- **但"存在"不等于"开放给你"。** `wb.request` 拿到的 `methods` 只有一个 `http.fetch`；另外两个管道是 `wb.entitlement` 和 `wb.wecom-a2a`。微信那条路确实在这儿，**可它是 WorkBuddy 自己的内部 A2A 通道**，不对第三方开放会话控制。`session/list` 直接回 `E_CHANNEL_UNKNOWN`。
- **结论因此变了性质**：不是当初设计偷懒，而是**外部 hook 这艘船到不了那里**——它能做的只有「把内容塞进用户下一次上下文」。这句结论比「做不到」有用得多，因为它同时说明了**为什么**以及**该去哪里找替代**。

- **顺着结论找到了真正能做的那一步**：官方文档点名的「stdout 会进上下文」有两个例外（`UserPromptSubmit` 和 `SessionStart`），而过去只挂了前者。补上后者之后，因为 WorkBuddy 每一轮都会补发 SessionStart（昨天刚好因为这个 bug 查清了它），信在**会话 resume 的那一刻**就到了，不必等用户真的开口。
- **下半句（文案）也是 bug 的一部分。** UI 上写着「信会在你下次在 WorkBuddy 里说话时一起送到」——用户那句「很蠢」有一半是被这句话激出来的。**把机制的真实边界写进文案，比让用户自己脑补更重要**；反过来，文案掩盖机制的时候，它会替你揽下所有骂名。
- **顺手补了一条真并发断言**：两个入口意味着 `UserPromptSubmit` 和 0.1 秒后的 `SessionStart` 是**两个独立进程**同时抢同一封信。串行测试只能证明"取过一次后没了"，证明不了竞态，所以这里用 `Promise.all` 同时发起，断言恰好一个拿到。结果证明 `take()` 那句「先 rename 到 sent 再算投递成功」本来就顺带解决了它——**一个为了防"黑洞"写的原子操作，同时也防了"双投"，而写它的人当时未必想到第二个场景**。

## 2026-10-29 · 一个现象 ≠ 一个 bug：「thinking 时显示 idle」有两个根因，在两个文件里

用户前一天报的「thinking 的时候状态为 idle」，我搁置了一天，理由是「等你的 `events()` 输出」。**那是偷懒**——这两个根因在这台机器上翻代码就能静态定位，而且证据是现成的。承认这一点很重要：把「需要更多信息」当成不动手的理由，是最容易伪装成严谨的拖延。

**先让自己看见，再动手改**：我先把 WorkBuddy 的真实事件序列写成一条断言跑一遍，`thinking → idle` 当场打印出来。这一步把「我认为根因是」变成了「我看见根因是」——**改 bug 之前先写一条会红的断言，是唯一能把猜测变成证据的办法**。

**根因一在 `src/state.js`**：`SessionStart` 被当成「切回 idle」。而 WorkBuddy **每一轮**都会在 `UserPromptSubmit` 之后约 0.1 秒补发一个 SessionStart（首轮 source=startup，之后全是 resume）。于是真实链路是 `thinking →（0.1s）→ idle → 挂一整轮`。Claude Code 只在真正开会话时发一次，所以这个误会错很久也不暴露——**一条能在参考实现上正常工作的语义，不等于它是对的**。

**根因二在 `hooks/clawd-hook.js`，和状态机隔着一个进程**：`field(payload.session_id) || "unknown"`。缺会话号的事件被塞进同一条幽灵会话，于是**多条真实会话的事件互相覆盖**：A 正在 thinking，B 结束发一个 `Stop` → attention 播完 800ms → 整条会话回落 idle，A 的画面就变 idle。这条比第一条更隐蔽，因为它坏在「谁能看见真相」的层面，而不是映射表写错了。

- 用户只会描述现象，而且**现象是多个 bug 叠加后的样子**。指望「一个现象对应一处代码」是天真的。
- 修语义时旧断言红了，**先判断它红得对不对**。这次「idle 累计够久就睡着」那条红了——它依赖的正是被证明错误的旧语义，红是完全正确的，改口径不是迁就失败，是纠正假设。
- 反过来，如果它没红，我反而该怀疑：**是不是我的修复根本没生效**。

## 2026-10-29 · 另一个仓库的注释里，写着这个 bug 的答案

两个根因都不是我从 starter 的代码里推出来的，是**主仓库 `hooks/workbuddy-hook.js` 的注释直接告诉我的**：第 264 行写清了 SessionStart 补发 0.1 秒这件事，第 233 行把 `session_id` 缺失那条挂上了真实事故编号 #618 / #648。

- 双仓库的价值不在抄代码，在于**主仓库踩过的坑留下了带编号的记录**。它是这个项目的错题本，而错题本通常比教材有用。
- **方法**：遇到「本仓从没见过的现象」，第一步别在本仓里皓首穷经，先去主仓库 grep 那个现象的具体关键词（`SessionStart`、`session_id`、`agent_id`）。这次从「我记得先称之为 agent 的这一轮发生了什么」到定位两个根因，全程没跑一次真实会话。

## 2026-10-29 · 觉得它「圆」，先别缩放，看它是不是个正椭圆

用户的原话：「肚子现在太圆了。还有一处是像脏了一样，微调一下布偶猫的身体」。两句话是两件事，第二句比第一句好修。

**先说"像脏了"的那处**：它是 `#rig-torso-patch`，一个 `<ellipse cx="112" cy="134" rx="34" ry="18" fill="#EFE6DC" opacity="0.65"/>`，注释写的是**「背部柔毛轮廓」**。读起来却是污渍，四个原因叠在一起：在一只有 3.5px 描边的猫身上它是唯一**没有轮廓**的形状、它比身体**暗一档**、位置**偏右上**（不对称的东西会被当成意外而不是设计）、边缘是硬边没有羽化。删掉之后世界安静了——白猫的肚子本来就该是白的，体积感由描边 + 呼吸缩放 + 地面阴影三样提供，不需要再叠一块"暗部"。

- **一个注释说 A、看起来像 B 的部件，它实际上就是 B**。「背部柔毛轮廓」是当初写它的人给自己的行为找的解释；用户第一眼把它读成脏东西，那它就是脏东西。**注释描述意图，观感才是事实**——两者打架的时候信后者。

**再说"太圆"**：第一反应是调 `rx/ry` 缩一圈。但真正的圆感来源不是尺寸，是**曲线本身**——`#rig-torso` 是个 `<ellipse rx="54" ry="32">`，完美椭圆弧上每一点的曲率都在说"这是个圆"，而**动物身上一处纯椭圆轮廓都没有**。

- **判断"该改数值"还是"该换曲线类型"的办法**：把它在脑子里缩放一下，那个别扭的感觉会不会跟着缩放一起消失？椭圆缩到任何比例仍然是椭圆，所以"圆"这个感受会跟着缩放一起留下来——说明它在曲线类型里，不在数字里。这时候改数值只会让你在**"缩到露出缺口"和"放到还是个球"**之间来回弹，而且会一直以为是自己数值没调好。

## 2026-10-28 · 在被读到之前，stdout 不是日志，是协议

排版这段时一直有个别扭：文件头的铁律写着「绝不打日志，stdin 里有用户 prompt」。
而 `deliverLetters()` 恰恰往 stdout 写字。

- 想清楚了就不矛盾：**那几行字节不是给"人"看的诊断信息，是给宿主解析的协议输出**。铁律要防的是"把用户的 prompt 打进控制台/日志文件"，不是"不许和宿主通信"。
- 但紧跟着一个真问题：**没有信的时候必须一个字节都不输出**。`UserPromptSubmit` 的 stdout 会被并进用户这一轮的消息里，多打一个换行都是在污染**每一次**对话。所以这条做成了回归断言，用真子进程数 `out.length === 0`，不靠读内部变量猜。
- 还有一个更阴的坑：`process.exit(0)` 在管道上**会截断还没 flush 的输出**。截断的 JSON 在宿主那边就是"没有输出"——信白寄，而且零报错。所以输出改成了 `await new Promise(r => process.stdout.write(payload, r))`，写完再退。
- **教训**：凡是"写完就退出"的短命进程，都要问一句"我写的东西真的落地了吗"。这类 bug 的特点是**只在大 payload 或慢管道上出现**，本地手测永远碰不到。

## 2026-10-28 · "顺序"这种用户能感知的属性，别交给 UUID 兜底

回归里「取信按写入顺序、一封不漏」红了。一开始以为断言写错了，查下去是**真 bug**：

- 信按 `createdAt` 排序，`createdAt = Date.now()`。两封信完全可能落在**同一毫秒**里，这时排序走进兜底分支 `a.id < b.id`——而 id 是 UUID，**等于随机**。
- 于是"先写的先寄出"这个用户唯一能感知到的语义，在快写的情况下就没了。手写碰不到（人的手速不会同毫秒），脚本和回归能碰到。
- **修法**：`createdAt` 至少比现有最晚那封晚 1ms。代价是时间戳可能超前几毫秒，对 24h 的过期判断毫无影响。
- **更值得记的是断言**：我一开始只验"第一封排在最前面"。这条在 bug 存在时**也可能通过**（碰巧）。所以补了一条直接验不变量——`letters.every((l,i,a) => i===0 || l.createdAt > a[i-1].createdAt)`。**验结果不如验不变量：结果可能碰巧对，不变量不会。**

## 2026-10-28 · 别自己发明握手，用宿主的事件

信纸窗口第一次打开时有个经典问题：`loadFile` 是异步的，页面脚本还没跑完就 `send` 消息，消息会丢。

- 气泡窗口的解法是**握手**：渲染层注册完监听器后回发一个 `letter:ready`，主进程收到才投递。这在本项目里是有历史的（S5 踩过"第一个权限气泡永远空白"）。
- 但信纸这里我改用了 `did-finish-load`。差别在于**可靠性归属**：
  - 握手的可靠性取决于"页面脚本有没有跑到那一行"。页面脚本一抛异常，握手永远不来，表现是**双击毫无反应**——一个完全静默、还很难查的失败。
  - `did-finish-load` 是宿主自己管的，页面再烂也会触发。
- 顺带删掉了 preload 的 `ready()`、渲染层的 `ready()` 调用、主进程的 `letter:ready` 处理——**换机制就要把旧机制的残骸清掉**，不然下一个人会以为两套都在用。
- **教训**：握手是为了解决"谁先谁后"，如果宿主本来就有"我准备好了"的事件，就没有"谁先谁后"的问题。

## 2026-10-28 · 为了"可测"而牺牲真实体验，是最容易通过评审的那种错

- **现象**：给 `theme.json.timings` 加 SleepAfterMs 时，为了让"主题里确实有个值"好看，给 ragdoll 写了 `sleepAfterMs: 20000`（内置默认是 60 秒）。用户第二天就报：**"working 的过程中不知道什么时候就睡觉了，然后又敲键盘，然后又睡觉"**。

  1. **口径本身就错**：判定写的是 `now - lastAt > sleepAfterMs`（多久没收到事件），而不是"idle 多久"。一次跑 40 秒的构建期间没有任何事件，于是"没消息"被当成了"没在干活"。

- **这条待办是错的**：它把"代码里有个常量"当成了"这是个配置项"。25 秒发呆这件事从来没有发生过，只是有人想过。**台账也会记错，而且错得很有说服力**——它带着具体数字，读起来像实测。
- **差点犯的错**：如果顺手把它一起搬进 `theme.json.timings`，就是硬约束 25 刚立的那个事故——主题作者写了 `idleAfterMs`，校验通过、加载成功、什么都不发生。**规矩立完不到一小时，最容易在自己手上破。**
- **判据没变**：这个字段有消费者吗。没有 → 不搬，删掉，把它那个没解决的问题留进注释（长工具调用跑 40 秒期间没有任何事件，会被误判成闲置——真要做，先回答这个）。
- **真正搬的是** `ONESHOT` 三个时长 + `SLEEP_AFTER_MS`，因为它们每 250ms 都在被 `tick()` 读。**搬之前先 grep 一遍引用数**，比读注释可靠。

## 2026-10-28 · 新断言要有对照组，否则它可能一直在测别的东西

- **现象**：给 `timings` 写断言，第一版只测了「主题写 60ms → 220ms 后退回 idle」。过了。但这个断言**换个实现也能过**：万一 attention 本来就只有 60ms 呢？万一 `getTimings` 根本没接上、只是默认值碰巧很短呢？
- **修法**：每条都配一个**对照组**——`getTimings: () => null` 时，220ms 后必须**仍在** attention（默认 2400）、仍是 working（默认 60 秒）。两组一起过，才证明「差别来自主题写的那个值」。
- **同一个道理的另一面**：`timings` 没写时，`theme.js` 返回 `null` 而不是编一份默认。**默认值的真相只能有一份**（在 `state.js`），两边各存一套时，分叉是静默的——你会看到"主题 A 睡得快、主题 B 睡得慢"，查半天。所以「没写就读作 null」本身也有一条断言。
- **还挡了一条**：主题只能在 `ONESHOT` 已有的三个键上改时长，给 `working` 写时长也不能把它变成 oneshot。否则一个主题就能让「工作中」播 2 秒就消失——**那是改状态机的形状，不是改外观**，而且改完是静默的。

## 2026-10-28 · 台账里的数字，得是跑出来的那个数

- **现象**：台账四处写着「回归 103/103 全绿」。跑出来是 **102 PASS / 0 FAIL**。差的那条是「剪贴板拿到的是完整路径」。
- **它不是失败**：那段逻辑先重试 6 次读剪贴板，读不到就写一次 `PROBE-OK` 再读回来做能力探测；**探测也失败才走 `[warn]` 跳过**——这是为「CI 里没有剪贴板」设计的降级，既不 PASS 也不 FAIL。
- **为什么会写错**：103 是**声明**的断言条数，102 是这次**实际报到**的条数。写台账的时候顺手把「声明数」当成了「通过数」，还配了个「全绿」——**「全绿」这个词最危险，它听起来像"每一条都验过了"，实际是"没有一条报 FAIL"**，而走 warn 的那条根本没验。
- **教训**：台账里的数字必须是**上一次真跑出来的数字**，而且要连同降级路径一起写清楚。否则下一个人看到 103 全绿，会以为剪贴板那条也验过了——这就是同一个「假绿灯」换了件衣服。
- **同类**：上面「永远为真的断言」是**判据**上的假绿灯；这条是**统计口径**上的假绿灯。共同点是：都能在报告里混过去，都不需要撒谎，只要不细看。

## 2026-10-28 · 功能下线时，删掉"消费者"是不够的

- **现象**：用户说「还是不要摸鱼了，改为敲打键盘」。这是把上一轮刚做完的钓鱼彩蛋整个否掉。删干净 `renderer.js` 里的彩蛋引擎和两个部件，十分钟的事。
- **但删完之后**：`src/theme.js` 里还留着 150 行 `normalizeMotion` / `normalizeGags` 校验器，`themes/README.md` 里还写着完整的 `gags` schema（含示例 JSON、字段表、"三条容易踩的"）。**主题作者照着写，会校验通过、加载成功、什么都不发生。**
- **为什么这比留着代码更糟**：留一段没人调的代码，至少 grep 得到、读代码能看见"这里没人用"。留一个**活的校验器**，它会在加载日志里给你一个"嗯，这个主题没问题"的信号——一个假的绿灯。
- **判据只有一个**：这个字段还有消费者吗。没有，就连校验、文档、回归断言一起删。
- **同类**：回归里那条「motion 声明的部件在 SVG 里都存在」——`def.motion` 永远是 `undefined`，`for` 循环一次都不进，**断言永远为真**。它每个月都在报告里 PASS，长得像一道防线。删掉它的时候我犹豫了一下（"以后恢复 motion 不就用上了"），答案是恢复的时候再写。

**顺带踩到的一个真漏洞**：`src/renderer.js` 里有一行 `this.rootLayer.innerHTML = createRiggedRagdollSVG()`，**违反硬约束 19**（`src/` 下 innerHTML 必须为 0），而且活了整整一轮。它不报错、不崩、画面正常，因为模板是我们自己的字符串——于是所有人都觉得它"不算"。可那条约束本来就是为了防"下一次 `innerHTML` 里出现外部数据"。**写在台账里的规则，如果没有人执行，它的状态永远是"未知"而不是"满足"。** 现在它是一条扫文件的断言了。

## 2026-10-28 · 「有这个出口」和「这个出口有货」是两件事

- **现象**：回归救到 104/105，最后一条「弹簧通道都建起来了（≥20 个）」报**通道 0 个**。rig 里明明有 28 个 `SpringChannel`，不可能没有。
- **原因**：`petDebug.springs()` 里写的是 `ragdollRig.springs`，而 rig 构造时写的是 `this.sp = { … }`。名字对不上，`if (!…) return {}` 干干净净地返回空对象。
- **为什么不早发现**：返回值是 `{}` 而不是 `undefined`，更不是抛错。调用方（回归）拿到空对象后自己就判断通过了——我们这条新断言拿到 `{}` 才算失败。**在写这条断言之前，它沉默了整整一轮。**
- **教训**：这是同类事故的第四次（前三次：CSP、白名单不在路径上、`VISUAL_STATES` 消失）。前三次还能被回归数量提醒，因为一坏就坏一大片；这种「单点接错」的只有**主动为它写一条自检**才会暴露。所以硬约束加了一条：**`petDebug` 的每个出口要么删掉，要么有一条断言证明它返回的是真东西**（不是 `{}` / `null` / `[]`）。

**顺带一条关于查错顺序的**：这条断言本来是我为了让「28 个通道」这个说法有个依据才加的，结果它立刻揪出一个真 bug。**断言的价值常常不在它守的东西，而在逼你先把基数读出来**——「理应是多少」这个问题一旦提出，`0` 就藏不住了。

## 2026-10-28 · 探针要选「每帧从零算出来的量」，不是「会收敛到定值的量」

- **现象**：想证明「骨头版也在动」，于是连续 12 次读 `petDebug.springs()`——12 次快照**一模一样**，判成没在动。而同一时刻猫明明在呼吸。
- **原因**：弹簧的**目的**就是收敛到目标值。working 是个稳态，进入 1 秒后所有通道都到位了，读数当然不再变。**拿一个"追求不变"的量去证明"在变"，逻辑上是反的。**
- **修法**：改读每帧由正弦直接推导、不经弹簧的那几个 transform（`rig-body-group` 的位移含 `breathSin`、`rig-ruff` 的缩放含 `breathCos`、尾巴的 `d` 每帧重算），实测 12/12 全不相同。
- **教训**：写「XX 在动」这类断言前先问一句「这个量稳态时会不会停在某个值上」。会停的量只能用来测**过渡**（切换、收敛），不能用来测**持续**。

## 2026-10-28 · 写进去 `3.80px`，读出来 `3.8px`

- **现象**：断言期望 `translate(3.80px, -2.80px)`，实测稳定读到 `translate(3.8px, -2.8px)`，红得很固执。
- **原因**：我们是 `el.style.transform = "…px"` 写进去的，再经 CSSOM 读回来时**已被重新序列化**——尾零按 CSS 数值规范被去掉。`toFixed(2)` 只是决定了「写的时候保留两位」，管不了浏览器怎么串回来。
- **修法**：判据改成**数值 + 容差**（两个分量各自差 0.06 以内就算到），不再比字符串。
- **教训**：凡是经过 Web API 序列化回来的值（CSSOM、`getBoundingClientRect`、`JSON.stringify`），期望值一律走数值比较。「写着一模一样的期望却在红」时，先怀疑中间层把值改写过，而不是怀疑断言写错了。

**同为这一类**：替换代码块时用一个「区块内部也会出现」的字符串当终点锚点（`index('…')`），命中了更早的那一次，切片过短，新旧代码块叠在一起 → `Identifier 'gagA' has already been declared`。**终点锚点必须选在区块之后**，或者干脆按行号切片。

## 2026-10-28 · 重写最容易丢的不是功能，是那两道「没用的闸」

- **现象**：用户拿来一版外部重写的渲染层，说「加载失败了」。修完 `schemaVersion` 就通了，画面比以前好看得多、切换也更顺。看起来是一次成功的升级。
- **问题**：这一版同时**删掉了 CSP**、把主题帧的注入口从 `svgNode()` 改成了 `innerHTML = frames.join("")`、删掉了 `window.VISUAL_STATES`。三件事都不报错、不崩、画面正常。
- **为什么会被删**：因为它们当时的**效果**是零。CSP 挡住的东西一个都不在（没有内联脚本、没有远程请求），白名单挡住的东西一个都不在（主题都是自己画的），`VISUAL_STATES` 只是调试用的。**从「今天能不能跑」看，它们全是冗余。**
- **代价**：白名单从「唯一的出口管控」退化成「文件里几个没人调用的函数」。审计时 grep `sanitizeSvg` 会得到「有」，于是防线看起来还在——**留着但不在路径上，比删掉更危险**。
- **教训一**：防线类的代码，评价标准不是「它今天拦住了什么」，而是「明天漏了还剩什么」。这类代码永远通不过「有用性」审查，所以需要一条**可机械检查的硬约束**（`innerHTML` 出现次数 = 0），而不是靠人记得。
- **教训二**：架构重写之后第一件该做的事，是**看回归掉了多少**。这次从 103 掉到 54。掉的 49 条里，38 条是「探针被删」、11 条是「断言假设过时」——但只有逐条看才知道，因为它们在同一个提交里一起变红，看起来像「测试过时了」。

## 2026-10-28 · 同一个字段的第二次死亡

- **现象**：`eyeTracking: false` 又不生效了——猫在那一版里是伏案打字（这一轮已改回水边垂钓），还在追光标。
- **原因**：上一轮刚修过一模一样的 bug（字段被 `theme.js` 校验、被 IPC 传输、渲染层从没读过）。这一版重写新写了 rig 分支，`applyGaze()` 里**无条件** `setGaze()`，老字段没人管。
- **为什么重写必然复发**：重写的人看的是「我要实现什么」，不是「原来那个 if 在守什么」。**新分支默认不继承老字段的语义**，而字段本身不会报错——它只是静静地没人读。
- **修法**：`applyGaze()` 把 `eyeTracking` 提到分支之前，统一算一次 `track`，rig 与帧路径都用它。**开关要先于分支计算**，否则每条新分支都要记得读一次。
- **教训**：声明式字段的「接上了」不是「有代码用到它」，是「**有一条会因它失败的断言**」。这次回归里那条 `working 的 eyeTracking 为 false` 一直红着——它其实一直在报警，只是被「测试过时了」的解释盖过去了。

## 2026-10-28 · 1.8px 的眼睑压不住 28px 的眼睛

- **现象**：给 working 设了 `eyelidTop: 1.8` 做「疲惫半睁」，截图看上去完全正常睁眼。
- **原因**：眼睑是一块从 `y=76` 往下压的矩形，眼球直径 28（`cy=92, r=14`）。压 1.8px 只挡掉 **6%**，肉眼根本分辨不出。要读成「半睁」得压到 11px 左右（约 40%）。
- **为什么写了却看不出**：作者心里的「半睁」是个形容词，落到代码里是绝对值。**形容词和像素之间没有换算表**，只能量：先算出目标部件有多大，再决定参数。这个主题里眼睛 28px、脸 74px、整个 viewBox 200px。
- **教训**：任何「轻微 / 明显 / 半」这类形容词参数，先量基准尺寸再定数值，否则一个数量级的偏差是常态。

## 2026-10-27 · 字段"写了"和字段"接上了"是两件事

- **现象**：给布偶猫的 working 状态写 `"eyeTracking": false`——猫在钓鱼，不该追着光标看。改了，跑起来还在追。
- **真相**：`theme.js` 校验它、状态对象带着它、IPC 送过来了，**渲染层一次都没读过**。`applyGaze()` 只管找 `.pupils`，找到就写 `transform`。这个字段从 S7 起就是死的，只是之前没有哪个状态需要它关。
- **为什么难发现**：它不报错、不警告，甚至"看起来生效过"——因为早期那些状态恰好都写了 `true`，而 `true` 和不看字段的效果一样。**一个永远为真的开关，和一个不存在的开关，运行时完全等价。**
- **修法**：`applyGaze()` 先看 `currentDef.eyeTracking`；同时给 working 补回一个 `.pupils` 组，让这个 `false` **有对象可管**。否则"不跟眼"只是"这张图里恰好没画瞳孔层"——那是巧合，不是功能，下一个人画出瞳孔就会自动失效。
- **教训**：每加一个声明式字段，配一条**能因它失败的断言**。这里的两条：「working 的 eyeTracking 为 false」+「working 下瞳孔不跟鼠标」+「idle 的为 true（对照组）」。没有对照组的那条断言，用"根本没有瞳孔"也能通过。

## 2026-10-27 · 还没到点的那一段，不许先写一遍

- **现象**：彩蛋第一段完全不动。鱼本该从水下浮上来，实测 300ms 时 `transform` 是 `translate(0.00 0.00)`。
- **原因**：`renderGag(t)` 遍历所有步骤，对还没到 `at` 的那一段做了 `clamp((t - at) / span, 0, 1)` = 0，于是**照着 `from` 写了一遍**。而同一部件的后一段 `from` 是 `[0, 0]`，它把正在演的第一段覆盖了。**"最后写的赢"这条规则，让一条没开始的规则赢在了起跑线上。**
- **修法**：`if (t < step.at) continue;`——没开始就不参与。语义随之变成"当前有效的那一段说了算"，也就是人读时间线时的直觉。
- **为什么第一版没测出来**：我测的是"有没有在动"（两次采样不同），而它**确实在动**——动的是第二段。**"在动"和"按预期在动"是两条不同的断言。**
- **教训**：凡是"按时间轴依次应用多条规则"的实现，明确三种状态：未开始 / 进行中 / 已结束。把"未开始"当"已结束"处理，是最常见的静默错误，因为它只影响开头那一小段。

## 2026-10-27 · 收尾要"恢复原值"，不是"设成默认值"

- **现象**：鱼被吃掉之后，猫的**眼睛没了**。
- **原因**：彩蛋收尾对着 `parts` 里的每个部件执行 `setAttribute("display", "none")`。鱼和拖鞋本来就该藏，可 `pupils` 是**本来露着**的——它进 `parts` 只是为了"跟着看一眼鱼"，结果被当成一次性部件一起藏了。
- **修法**：开演前把每个部件的 `{display, transform}` 存一份快照，收尾按快照逐个恢复（原值不存在就 `removeAttribute`）。多一个 Map，换掉一整类 bug。
- **为什么原来那种写法很自然**：因为部件的"常态"在编写时只有一个——藏着。等到第二个用途（"临时接管一个常驻部件"）出现，那个隐含假设就崩了。
- **教训**：**任何"用完还原"的逻辑，还原的目标都必须是快照，不是你以为的默认值。** 同一个部件被不同用途复用时，这一点尤其致命——而且失效方向是"少画一块"，很容易被当成美术出错，而不是逻辑出错。

## 2026-10-27 · 想同时位移和缩放，除了再套一层没有别的办法

- **现象**：鱼被吃掉要靠"往嘴边移动 + 缩小"。写两条规则给同一个 `<g class="m-fish">`，结果只有一条生效。
- **原因**：SVG 元素的 `transform` 是**一个属性**，不是可叠加的样式列表（CSS 的 `transform` 才是列表）。`setAttribute("transform", "translate(a b)")` 会把上一句写进去的 `scale(...)` 直接顶掉。而我们的引擎每帧都在写。
- **修法**：内层再套一个 `<g class="m-fish-in">`，外层管位移、内层管缩放。两个元素各有一个 `transform`，互不覆盖。
- **教训**：这条要提前写进契约（`themes/README.md` 硬契约第 4 条），因为它**失败时不报错**——画面上只是"缩放没生效"或者"位移没生效"，看起来像参数写错了。凡是"一个属性承载全部变换"的图形系统，组合动作都必须靠**嵌套**表达。

## 2026-10-27 · 白名单要先定，再写加载器

- **场景**：S7 主题系统，主题文件是不可信输入。按老习惯想先写加载器（读 JSON、读 SVG、送进渲染层），觉得"白名单是清洗层的细节，后面调"。
- **改了顺序**：先在 `SECURITY.md` 写定案——哪个标签放行、哪个拒、为什么——再动代码。
- **如果反过来会怎样**：第一个主题大概率用 `filter` 做柔和阴影，然后加不进去，于是去 `ALLOWED_TAGS` 里加一行。此时心里想的是"让它能跑"，不是"这样安全"。加完也不会回头问 `feImage` 该不该一起放行。
- **实际定案的过程**：先读主仓库 `theme-sanitizer.js`（347 行），发现它用的是**黑名单 + URL 目标校验**，`clipPath`/`mask`/`filter` 全放行。我们没有照抄——starter 从 S3 起就是白名单，改成黑名单等于把强约束降级。最后是"白名单 + 窄口径放行"：三个标签放，`fe` 图元逐个列（不用通配），`feImage` 和 `feTurbulence` 单独拒。
- **教训**：**白名单是设计决策，不是实现细节**。它的内容取决于"这个产品要表达什么"，写在代码里就等于让它被"能不能跑通"绑架。

## 2026-10-27 · 间歇失败的测试比没有测试更危险

- **现象**：4 次回归有 2 次挂在「换状态时切换图层」，报 `layerB → layerB`。单看这个断言，像渲染层没换层。
- **第一次误判**：怀疑是主题异步到达和测试抢跑，加了"等主题加载"的断言——还是偶发。
- **真正定位靠一行日志**：给 `petDebug` 加了 `stateLog()`（最近 20 次状态推送），失败时打出来：
  `[{t:197,visual:"idle"},{t:309,visual:"idle"}]` —— **两次 idle，间隔 112ms**。
  于是真相是：状态机 tick 的 250ms 周期已经把 `lastVisual` 从 null 推成 idle，300ms 的"首帧保险"又推了一遍；测试恰好在两次之间把状态改成 working，第二次 idle 把它顶回去了。
- **修法**：应用侧去掉重复推送（`pushedAnyState`），测试侧动手前先等推送静默 400ms。
- **顺手加了一条永久断言**：「换一次状态只重建一次」。重建次数翻倍画面上完全看不出来（结果一样），但它是竞态的指纹。
- **教训**：调试"随机失败"时，**不要读代码猜，加观测点**。一行环形缓冲日志的价值超过半小时推理。另外——**别用放宽断言的方式让它变绿**，那等于把 bug 藏起来。

## 2026-10-27 · 断言不要去改被测对象

- **场景**：剪贴板那条断言一直"跳过"，因为探针写 `PROBE-OK` 后读回是空串，我据此推断"这个环境访问不到剪贴板"。
- **真相**：顺序写反了。`copyPath` 已经把路径写进剪贴板，接着探针 `writeText('PROBE-OK')` **把证据覆盖了**，然后断言读到的当然是 `PROBE-OK`。
- **修法**：先读真值 → 不等才做能力探测（并把原值写回去）。改完立刻拿到 `E:\work\proj-alpha`。
- **连带纠正**：上一轮"本环境访问不到剪贴板"的结论是错的，台账里已经改掉。
- **教训**：测试代码和业务代码一样会骗人。**任何"先做点什么再检查"的断言，都要问一句：我这一步有没有改变被测对象。**

## 2026-10-27 · 安全修复顺手砍掉功能，比漏洞更难发现

- **场景**：S2 审 SEC-09（cwd 泄露）时，修法写的是「cwd 只留 basename」。听上去干净利落，一天之内相安无事。
- **到 S6 才暴露**：看板要做「复制路径」和「跳转终端」，两者都需要完整路径。按原来的修法，功能根本做不出来。
- **关键判断**：这时候有两条路——① 放弃功能，继续只留 basename；② 取消脱敏。两条都错。正确的是**分层**：存储层留完整路径（只活在主进程内存里），快照层只出 basename（会进渲染进程、上屏幕），完整路径唯一的出口是用户显式点击时由主进程单条释放。
- **教训**：「脱敏」的粒度应该按**数据流向**切，不是按字段切。一刀切掉字段，看起来最安全，实际是**把风险转嫁成了功能缺失**——而功能缺失不会出现在安全报告里，所以永远不会被回头修。
- **同类检查项**：以后凡是写「只保留 X」，都问一句「有没有哪条链路必须要完整的 X」。如果有，就得分层，而不是砍掉。

## 2026-10-27 · 测试跑不起来，八成不是代码坏了

- **现象**：改完代码跑 `npm run verify:electron`，报「渲染进程 15s 内没起来」。第一反应是渲染层被我改崩了。
- **真相**：用户自己开着桌宠。单实例锁 + 固定端口 23333 让测试进程启动即退出。
- **修法**：不是"跑测试前先关掉桌宠"，而是让测试**自隔离**。`requestSingleInstanceLock()` 是按 `--user-data-dir` 分实例的，所以 spawn 时换一个临时 userData 目录、顺带把 `CLAWD_PORT_FILE` 也指过去，测试就变成"另一个应用"。
- **教训**：**「需要用户先做点什么」的测试，等于没有测试**。它一定会被跳过——正好是你最需要它的时候。让测试自带隔离环境，成本只有十来行代码。
- **附带一次险情**：为了清场我执行了 `taskkill /IM electron.exe`，差点杀掉用户正在用的桌宠（这个项目自己的进程也叫 electron）。靠 `Get-CimInstance Win32_Process` 查命令行才拦住。**永远不要按镜像名杀进程。**

## 2026-10-27 · 一只眼睛不动：`querySelector` 从不告诉你"还有第二个"

- **现象**：换完形象，用户反馈"有一只眼睛不跟着鼠标转"。不报错、不警告、画面看起来只是"有点怪"。
- **原因**：画眼睛时图省事，给左右眼各包了一个 `<g class="pupils">`。而渲染层是 `el.querySelector("svg.on .pupils").setAttribute("transform", …)`——**`querySelector` 只返回第一个匹配**，所以只有左眼转了。右眼不是"没有动效"，它根本收不到任何指令。
- **为什么容易犯**：`class` 在别的框架里常被当成"标记一类元素"用，多份是正常的。但在这里，`pupils` 这个名字承载的是**唯一性语义**（"那个瞳孔层"），DOM 结构必须配合这个语义。命名和结构脱节，是这类 bug 的温床。
- **修法**：两只眼的瞳孔收进同一个组，组内坐标用绝对值（渲染层会整个覆盖 `transform`）。
- **教训**：凡是 `querySelector` + `setAttribute` 这种"拿到就改"的写法，都要问一句「这个东西会不会有多个」。**更要紧的是给它配断言**——回归里现在有「每帧最多一个 `.pupils` 组」和「瞳孔层里两只眼都在」，前者防复发，后者防"合成了一个但漏画一只眼"。

## 2026-10-27 · 预判写错了坐标系，五条要求四条作废

- **场景**：S5 开工前按惯例先写"五条安全要求"，写得很细：一次性 nonce 绑 `session_id` + `tool_use_id`、nonce 只走 stdin、默认 deny、回包要过 Host + token。
- **发现**：全错。写预判时脑子里默认 `PermissionRequest` 和 S4 的观察型 hook 一样是 **command hook**（起个短命进程读 stdin）。去主仓库 `hooks/install.js` 一看，它是 `type: "http"`：**Claude Code 直接 POST 我们的端点，HTTP 响应就是决定**。没有中间进程，没有 stdin。
- **连锁后果**：没有"独立的回包步骤"→ nonce 无从谈起（请求即响应、同一个 socket，决定天然绑在请求上）；没有 stdin → 第 2 条整条作废；调用方是 Claude Code 自己 → 它读不到端点文件，token 根本校不了；默认 deny 是错的 → deny 让工具**静默失败**，用户还以为自己批准过，正确做法是 204 不做决定、回落原生提示。
- **教训**：**预判的价值在于"写下来"，不在于"写对"**。但前提是预判必须在读源码之前标成"假设"，读完源码立刻核对、错了就整条重写而不是打补丁。四条错预判如果只是逐条打补丁，会得到一个"每条都做了点事、但都不对"的实现。
- **顺带学到**：真需要 nonce 的是**远程审批**——决定来自公网、可重放。主仓库的 nonce 只出现在 `telegram-native-runner.js`，`/permission` 那条路径上根本没有。这个区分以后再遇到类似设计时可以直接套。

## 2026-10-27 · 表现为"慢"而不是"错"的 bug 最难发现

- **现象**：启动后的**第一个**权限请求永远不弹内容，气泡空白，点了没反应，2 分钟后静默回落到终端。第二个开始正常。
- **原因**：气泡窗口懒创建。`webContents.send` 发出去的时候，渲染层还没执行到 `bubbleRenderer` 的监听注册，这条 IPC 被**静默丢弃**——不报错、不排队、不重试。Electron 的 IPC 就是这样，发早了就是没了。
- **修法**：握手。渲染层注册完监听后回一个 `bubble:ready`，主进程在此之前用 `bubblePendingEntry` 暂存，收到握手才真正投递。
- **为什么难发现**：它不崩、不报错、日志干净。用户看到的是"有点慢"，开发者会归因到网络、到 hook 超时、到系统负载，就是不会想到"消息发早了"。**这类 bug 只有断言能抓**——回归里那句「气泡显示了工具名」就是为它写的。
- **推广**：凡是"主进程推、渲染层收"的链路，只要渲染层是懒创建的，第一次投递就必须有握手。这和 S1 主窗口不一样——主窗口 `ready-to-show` 之后才 show，天然避开了。

## 2026-10-27 · 退出时的收尾不是洁癖，是 10 分钟的卡死

- **场景**：用户关掉桌宠的瞬间，Claude Code 可能正卡在一个 `PermissionRequest` 上等回应。
- **如果不管**：那条 HTTP 连接既不断开也不答复，一直悬着。hook 侧写的是 `timeout: 600`，所以终端最长 **10 分钟没有任何反应**，而气泡已经不在了，用户完全无从判断发生了什么。
- **做法**：`before-quit` 里 `permissions.dispose()`，把仍 pending 的请求全部以 204 结束。204 让 Claude Code 立刻回落原生提示，用户切到终端照样能批。
- **容易写错的地方**：`dispose()` 走 `settle() → onResolve()`，而 `onResolve` 里有"弹下一条"的逻辑。写得不对就会在退出过程中新建一个浏览器窗口，或者把排队项漏成悬空连接。所以回归里**同时挂两条**（一条在显示、一条在排队）来覆盖，只测一条测不出来。
- **教训**：任何"资源在退出时释放"的逻辑，都要问一句「如果还有人在等这个资源呢」。`server.close()` 等的是连接，而连接的对端是一个真实在等的进程。

## 2026-10-26 · Electron 的安全默认值是"半个"默认值

- **场景**：给 S1-S3 做安全审计，本以为 `contextIsolation: true` + `nodeIntegration: false` 就基本安全了。
- **发现**：这两个确实是关键项，项目里也都写对了。但 Electron 的安全面远不止这两条——`sandbox` 依赖版本默认、`webSecurity` 没写、`index.html` 没有任何 CSP。三个都没配，等于「门锁好了但窗户开着」。
- **另一个更隐蔽的**：本地 HTTP 服务不校验 `Host` 和 `Content-Type`。因为 `text/plain` 是 CORS 简单请求、不触发预检，**任意网页**都能往 `127.0.0.1` 发 POST 且拿不到响应也无所谓——副作用已经发生了。这类"本地服务信任边界"问题在 Electron/桌面端特别常见。
- **教训**：桌面应用的威胁模型和 Web 不一样。Web 里"跨域被拦"是一种保护；桌面端本地端口是**没有同源策略**的，必须自己补 Host/Origin/Token 三件套。

## 2026-10-26 · 把"未来会变危险"的地方提前标出来

- **做法**：审计时把问题分成「现在的影响」和「S7 之后的影响」两栏，比如 `renderer.js` 里的 `innerHTML`。
- **为什么**：现在 `markup` 来自本地常量，完全安全；但 S7 主题系统会从磁盘读第三方 SVG 字符串，同一个 `innerHTML` 立刻变成标准 DOM XSS 入口。如果只按当前风险评为"无风险"，等 S7 开工时没人会想起来回看。
- **教训**：给问题标「触发条件」，比标「严重度」更能防止遗忘。严重度决定先修谁，触发条件决定什么时候必须修。

## 2026-10-27 · 同一套判据写在两个脚本里，只改了一个

- **现象**：S7 收工终检，`check-filemap.js` 报 `[ok] 台账与文件系统一致`，`daily-check.js` 同时报「FILE_MAP 漏记 43 个文件」并 exit 2。两份脚本判的是同一件事。
- **原因**：`themes/**` 是「整目录登记」条目。`check-filemap.js` 早先改过，会把 `**` 结尾的条目抽成前缀参与覆盖判定；`daily-check.js` 里那段漏记检查还是老写法——`if (p.endsWith("*")) continue;` 把 `themes/**` 当通配项**直接丢掉**了，前缀没进比对集合，于是 `themes/` 下 43 个 SVG 全被当成未记录。
- **为什么危险**：报错的那个脚本输出更像「有事」，还带非零退出码；照它去补 43 条台账，就是把本已正确的台账改坏。**假警报比没警报更能误导人**，因为它看上去更负责。
- **修法**：把前缀逻辑原样搬进 `daily-check.js`，并注释写明两处必须同步。
- **教训**：同一条规则只能有一份实现。要么让一个 `require` 另一个，要么在两边都留一句「改这里必须改那里」。两处各写一遍、谁也没提对方，就必然在某次只改一处时劈叉。

## 2026-10-27 · 断言被测对象被环境反过来改掉了

- **现象**：「gaze 收敛到满幅位移」偶发失败，读到的值是 `translate(-0.98 0.81)`。看起来像"插值没收敛"，但又是个合理坐标，不像坏了。
- **原因**：主进程每 100ms 按真实光标位置推一次 `gaze`。测试注入 `{x:1,y:-1}` 之后，一条真实推送到达，把目标覆盖成光标位置；渲染层老老实实插值到光标——**它的行为完全正确**，错的是断言的前提（"注入的值会一直有效"）。
- **为什么费时间**：失败信息长得像 bug（一个不是期望值的坐标），实际是"收敛到了别的地方"。这类假失败最误导，因为被观测的那段代码根本没坏。
- **修法**：`petDebug.gaze(g, pin)` 加钉子，pin 期间忽略真实推送，断言完 `unpinGaze()`。
- **教训**：凡是「注入一个值 → 等它生效」的断言，动笔前先问一句：**还有谁会写这个值？** 只要有第二个写入方，就必须能独占，否则断言就是在赌时序。

## 2026-10-27 · 放宽容差别放成空壳

- **背景**：透明检测被背景噪声干扰（用户自己开着一只桌宠压在同一位置）。
- **第一版修法**：容差改成「背景噪声 + 2」。数字上很合理，也确实让断言稳定通过了。
- **问题**：实测出现 `noise=137, diff=137` 的角——那一块桌面本身就在剧烈变化，`137 <= 137+2` 成立，于是"通过"。可这个角**什么都没测到**。一条会自己静音的断言，比没有这条断言更糟：它让人以为检查过了。
- **修法**：噪声超过阈值（6）的角**不参与判定**，并要求至少 3 个可用角；可用角不足就打「跳过」而不是「通过」。
- **教训**：**容差一旦随环境浮动，就必须同时约束"可判定的样本数"**，否则容差会一路涨到断言失去意义。

## 2026-10-27 · "卡顿"不是帧率不够，是采样方式错了

- **用户原话**："每个动作切换也不丝滑，都是卡顿式切换。"
- **第一反应（错的）**：把 fps 从 8 调到 12、24。没用的，因为病根不是"帧不够多"。
- **真正的原因**：帧是**离散**替换的。8fps 意味着每 125ms 画面完全重画一次，中间 125ms 一动不动。
  人眼对这种"定住—跳变"极其敏感，再多几帧也还是同一个病——它长得像频闪，不像动作。
- **修法**：把动画从"换图"换成"改参数"。部件（身体/头/尾巴/眼睛）的位置每帧算一次，
  60fps 连续变化。同一个姿势图，靠插值就能呼吸、摆尾、歪头、眨眼。
- **教训**：判断"是不是动画问题"要看**时间的连续性**，不是看帧数。
  离散采样再密也有台阶；连续函数才没有。这条判断之后，`frames` 从 19 张降到 7 张，
  反而更丝滑——**帧数和流畅度根本不是一回事**。

## 2026-10-27 · 被白名单逼出来的架构，比原方案更干净

- 白名单拒 `<style>` 和 SMIL，主题里写不了 CSS 动画。当下的感觉是"限制碍事"。
- 但顺着这条限制走，动画只能放在渲染层：主题声明**意图**（哪个部件、怎么动、多快），
  计算全在我们自己的代码里。结果比"主题自带一段 CSS"好得多——CSS 是不可审查的，
  `motion` 是数据，能校验、能钳制、能测试。
- **教训**：安全限制常常把设计推向"数据和执行分离"这个更结实的位置。
  先问"这条限制逼我改什么结构"，而不是"怎么绕过它"。

## 2026-10-27 · 需要镜像的形状，别手算坐标

- **现象**：新画的猫耳朵变成了两根细天线。
- **原因**：左右耳用绝对坐标各算一次贝塞尔控制点，右边那组算错了（符号写反），
  结果就是两条细线。
- **修法**：只在局部坐标里画**一只**耳朵（宽 32、高 40、向上），再用
  `translate(...) rotate(...) scale(±1, 1)` 贴到头的两侧。镜像由矩阵负责，不由我负责。
- **教训**：凡是成对出现、只差一个镜像的东西，都该写成"一份形状 + 一次镜像变换"。
  手算两份坐标，等于给自己留一个必然发生的符号错误。

## 2026-10-27 · CDP 的 5 秒超时会把长断言变成"undefined"

- **现象**：新加的眨眼断言输出 `最小纵向比例 undefined`，但没有抛异常、也没有报错。
- **原因**：`R.eval` 底层 `send()` 有 **5000ms 超时**，超时后返回 `{error:{message:"timeout"}}`，
  `eval` 把它转成 `undefined`。而眨眼采样要在页面里跑 88×60ms ≈ 5.3s——刚好越界。
- **修法**：长采样不要写成"页面里的一个长循环"，改成**从 Node 侧逐次读**，
  每次 eval 都远小于超时窗口。
- **教训**：断言里的等待时间一旦超过工具链的默认超时，失败信息会变成 `undefined` 这种
  毫无指向性的东西。写采样型断言前，先确认"一次调用最多能跑多久"。

### `TypeError: Cannot read properties of undefined (reading 'whenReady')`

- **现象**：`electron .` 启动即崩，`require('electron')` 拿到的是路径字符串而不是 API 对象。
- **原因**：环境里存在 `ELECTRON_RUN_AS_NODE=1`（某些 IDE、CI 或别的工具设置过），Electron 退化成纯 Node 进程。
- **排查**：`env | grep ELECTRON`
- **绕过**：`env -u ELECTRON_RUN_AS_NODE npm start`（PowerShell：`$env:ELECTRON_RUN_AS_NODE=""; npm start`）

### 窗口全黑 / 出现灰色方块

- **原因**：`transparent: true` 必须同时配 `backgroundColor: '#00000000'` 和 `hasShadow: false`。
- **教训**：三个参数缺一个就露底色，这是 Electron 透明窗口的固定组合，不是可选项。

### 点不到、也拖不动

- **原因**：`setIgnoreMouseEvents(true, { forward: true })` 之后窗口默认不接收点击，只转发 `mousemove`。
- **解法**：必须在检测到鼠标压在宠物身上时显式调 `setIgnoreMouseEvents(false)` 切回来。
- **衍生坑**：窗口跟着光标移动后，光标在窗口内的相对位置不变，renderer 就再也收不到 `mousemove`——所以拖拽只能用主进程 `screen.getCursorScreenPoint()` 轮询，不能用 `-webkit-app-region: drag`。
