- **「指定哪个 session 就发到哪个 session」修好**（S14）。用户原话：「Deepseek harness，
  发送消息的时候，我需要实现的是，指定哪个 session 就发送到哪个 session 里」。
  - **先证明 DSH 没问题**：真 CLI 两轮实验——第一轮给它代号 `ALPHA-731`，第二轮带
    `--session-id` 问代号，它答 `ALPHA-731` 且 sessionId 没变。**测"是不是同一条会话"，
    最硬的判据是它记不记得上一轮，不是 id 一不一样**。
  - **根因 = 两个数据源覆盖范围不同**：看板从磁盘投影列**全量** DSH 会话，`say_send`
    却去状态机查 cwd，而状态机只收"最近还在动"的（`reconcile()` 的 `ACTIVE_WINDOW_MS`）
    → 历史会话一点发送就回「这条会话已经不在了」。反向那处 `compose_target_of` 的
    `can_resume` 只看磁盘投影 → 活态会话被误判"写不进去"，前端还**悄悄新起一条**。
  - **改法**：唯一查找入口 `main.rs::resolve_id()`（磁盘优先、状态机兜底；纯函数
    `resolve_target()` + 6 单测）。支撑 `dsh::ProbeView::target()`、`Store::live_target()`
    （多带平台）。**指定了目标就绝不悄悄换目标**：查不到/不能续/没目录都在 spawn 前报错；
    `ComposeTarget.reason` 由宿主写原因，界面不自己编。别家 agent 的会话不许塞进 dsh；
    DSH 的 `payload()` 现在显式写 `agent:"dsh"`（`unknown` 仍算 DSH 一侧兼容老数据）。
    刚启动 `polls==0` 查不到时提示「还在扫描」而不是"不在了"（真机第一次 e2e 就踩这个）。
  - **闸门手法（值得复用）**：造 npm 布局的**假 dsh** 放在子进程 PATH 最前面，
    `say::locate()` 走真实定位路径找到它；它只记录 **argv/cwd/stdin** 再吐两行 NDJSON。
    于是"指定哪条就发进哪条"可断言，且全程不调模型。反向两条还必须**一个进程都没起**。
  - **假阳性**：旧断言「目标行报出了目录」一直靠"写不进去"警告里的 `·` 通过，
    夹具根本没给 cwd；修对 bug 后它才红。→ 硬约束 56（断言要咬本体标志，别咬分隔符）。
